# Model Selection Guide Page

## Description

Reusable decision-support page for a concrete task family, model-team problem, portfolio decision, or other bounded model-selection assignment.

## Purpose

Lead a reader from an explicit assignment and constraints through evaluation evidence and trade-offs to a bounded, reviewable recommendation or evaluation route.

## Use When

Use when the page's primary job is choosing, evaluating, routing, or combining exact model identities for a defined purpose.

## Do Not Use When

Do not use for canonical factual model profiles, generic taxonomy categories, infrastructure selection, or broad operational guidance where the decision is not model-specific.

## Owns

- assignment definition and acceptance criteria;
- relevant constraints and failure severity;
- evaluation dimensions;
- exact candidate/version/artifact scopes where material;
- evidence states, uncertainty, conflicts, and missing evidence;
- task-bounded trade-offs and conclusions;
- re-evaluation triggers.

## Does Not Own

- canonical model identity facts that belong in Reference;
- provider claims presented as independent verification;
- unrelated infrastructure architecture;
- universal model qualities detached from assignment conditions.

## Expected Inputs

Requirement-approved assignment framing, constraints, acceptance criteria, candidate roles/identities, evidence basis, trade-offs, conclusions or evaluation hypotheses, verification date/conditions when material, and re-evaluation triggers.

## Composition

1. default header;
2. assignment and success criteria;
3. constraints/assumptions that materially affect the decision;
4. evaluation dimensions and evidence rules;
5. candidates or portfolio roles with links to canonical reference facts;
6. observed or expected trade-offs, limitations, and conflicting evidence;
7. bounded recommendation, shortlist, escalation route, or explicit unresolved outcome;
8. re-evaluation triggers and date-sensitive assumptions.

## Variants

Software-development selection, model-team portfolios, role-based portfolios, and future task-specific guides reuse this family unless their reader journey materially differs. Requirements may omit irrelevant sections rather than forcing empty headings.

## Representative Examples

- software-development model selection;
- model-team selection;
- role-based portfolios.

## Anti-patterns

- starting from a popularity ranking instead of the assignment;
- vague family-name recommendations when exact version/artifact identity matters;
- one aggregate score hiding evidence dimensions;
- transferring reliability across different tasks, quantizations, runtimes, or hosted routes without evidence.
