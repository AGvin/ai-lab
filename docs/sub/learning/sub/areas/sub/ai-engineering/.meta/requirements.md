# Documentation Requirements

## Requirements

- Present AI Engineering as the learning area for building, integrating, deploying, operating, observing, scaling, recovering, and costing complete AI systems around models, data, agents, software, and infrastructure.
- Keep model-internal training/inference mechanics with Models, agent semantics/control with Agents and Automation, reusable abstract system concepts with canonical concepts, and concrete product/provider facts with Catalog/Evidence owners.
- Explain that the currently materialized children include `infrastructure-and-hardware/` for source-backed infrastructure control-plane teaching, `cost-and-resource-management/` for source-backed system cost/resource teaching, and `reliability-and-resilience/` for source-backed bounded retry, fallback eligibility, and degraded-mode teaching.
- Do not imply that unmaterialized selected AI Engineering branches are absent from the logical architecture; standard navigation reflects only physical children.
- Teach engineering decisions through explicit system boundaries, authoritative state, measurable constraints/SLOs, failure domains, security/data boundaries, resource/cost behavior, observability, and recovery rather than assuming model capability alone determines production behavior.
- Keep mutable provider prices, quotas, APIs, instance types, regions, compatibility, benchmarks, and incident state source-backed with catalog/evidence/project owners.

## Validation

- AI Engineering owns complete-system integration/operations rather than intrinsic model or agent semantics.
- Current navigation exposes only materialized selected children.
- Mutable provider/product facts are not frozen as generic engineering truth.
- System state and operational evidence remain authoritative independently from model-generated descriptions.
