# Documentation Requirements

## Requirements

- Teach cloud and rented capacity as infrastructure whose lifecycle, cost, retention, and failure behavior must be controlled explicitly because resources can persist beyond the task that requested them and may continue consuming money, capacity, addresses, storage, or data-retention obligations after compute work ends.
- Use deterministic control-plane state for resource identity, desired/observed lifecycle, leases, ownership, admission, readiness, draining, teardown, retained children, and closure. Model-generated prose or worker self-reports are not authoritative resource records.
- For each managed resource class, define the provider/local identity and authoritative record schema; desired/observed states; owner/lease/expiry/fencing; capacity or mutual-exclusion group; readiness/admission probes; artifact-persistence requirements; drain/stop/delete/reconciliation policy; retained-child/billing/data-retention closure policy; and retry/quarantine/escalation authority where material.
- Normalize provider-specific state into a stable lifecycle that can distinguish declaration/reservation, creation/provisioning/start, readiness, busy/allocated, draining, artifact persistence, stop/termination/delete, stopped, cleanup/retained-child verification, billing/data-retention closure, and cleanup-failure/quarantine states as the workload requires.
- Do not jump from worker/task completion directly to `CLOSED`. Durable-artifact verification, compute shutdown, child-resource inventory, lease release, and billing/data-retention closure are separate gates that can succeed or fail independently.
- Keep roles explicit between task/request owner, deterministic resource controller, worker, artifact/result validator, exceptional-operation approval authority, and reconciler. One implementation may hold several roles only when authority and failure consequences remain acceptable.
- Before provisioning or loading, validate exact capability/workload requirements, model/runtime/hardware/storage/region/data policy, quota/budget/max lifetime, fallback policy, local capacity or mutual exclusion, stable operation identity/idempotency key, and a cleanup/recovery owner if the initiating process disappears.
- After an ambiguous create/provisioning timeout, query authoritative provider/local state before creating a replacement. A lost acknowledgement must not cause blind duplicate allocation.
- Separate liveness from readiness. A readiness contract can verify expected resource identity/region, model/artifact/runtime revision, storage/network access, intended device placement, required modalities/context/tools/schema, bounded capability probe, and tested memory/latency/capacity envelope where material.
- A reachable proxy, open port, healthy process, or generic HTTP success is not proof that the intended AI workload is ready on the expected resource.
- Use leases and monotonic fencing generations when multiple controllers or recovered processes can compete for the same resource. Lease expiry without cleanup can leak cost; a lease without fencing can allow stale controllers to mutate or terminate a resource now owned by a newer generation.
- Before job admission, verify lifecycle/readiness compatibility, tested queue/RAM/VRAM/disk/context/concurrency capacity, data and permission boundaries, remaining deadline for work plus validation/persistence/cleanup, and absence of conflicting ownership in shared resource groups.
- Define residency policy explicitly. Distinguish soft idle/drain behavior from hard maximum lifetime; health probes or incidental traffic must not keep expensive resources resident indefinitely unless policy intentionally allows it.
- Before destructive teardown, verify all required outputs are durable outside ephemeral storage. Where material verify destination, expected objects, sizes/checksums, provenance/config needed for reproduction, downstream readability/access, retention/deletion rules, and resume state.
- A successful upload/copy request is not proof that required artifacts are complete, readable, durable, or attributable to the correct run.
- Teach a safe teardown sequence as an explicit state machine: stop new admission; inventory/drain active work; persist and validate artifacts; request unload/scale-to-zero/stop/terminate/delete idempotently; poll authoritative state; verify local process/device release; enumerate compute/endpoints/storage/snapshots/addresses/caches/files/sessions/reserved capacity and other children; retain only explicitly owned resources; retry/escalate cleanup failure; and release leases/close only after required billing/data-retention evidence is complete.
- A stopped compute instance or endpoint can still leave billable or data-bearing children. Closure must include the resource classes that matter for the provider/local environment rather than relying on the parent compute state alone.
- Use periodic reconciliation in addition to callbacks/events when leaked, stale, duplicated, orphaned, or contradictory resource state matters. Reconciliation should enumerate system-owned resources, match authoritative records, fence stale owners, resume persistence/cleanup, verify closure, and surface unresolved cost/data exposure.
- Reconcile after controller restart and provider/network outages instead of assuming missed callbacks or events will self-heal.
- Define degraded/failure behavior for capacity/quota exhaustion, created-but-unreachable resources, wrong model/runtime readiness, load/OOM failure, artifact persistence failure, stop accepted while resource stays active, credential expiry during cleanup, controller crash in intermediate states, provider-state contradiction, or network partition during create/terminate.
- Depending on policy, recovery can use bounded retry, replacement, restoration of prior resident capability, separately validated fallback, queue-with-expiry, fail-closed cancellation, quarantine, or human intervention. Recovery must reconcile authoritative state before repeating consequential resource operations.
- Teach fit for on-demand GPU/media services, local mutually exclusive model residency, always-on generalists with temporary specialists, asynchronous hosted jobs, autoscaled endpoints/warm pools, resources whose cost or data retention persists beyond inference, and systems that must recover after controller failure.
- Avoid a dedicated lifecycle control plane when an operation is genuinely stateless and exposes no customer-managed lifecycle object, or when one simple local process has no meaningful dynamic load, shared-capacity, persistence, or cleanup risk.
- Evaluate provisioning/readiness success, duplicate allocation and stale-owner incidents, cold/warm startup, useful versus idle/provisioning/draining/leaked cost, artifact durability/checksum success, stop-to-stopped and stopped-to-closure latency, orphan count/duration, cleanup retries/quarantines/human interventions, and infrastructure cost per accepted result.
- Keep concrete provider states, APIs, instance/SKU identifiers, prices, quotas, regions, storage products, current billing rules, and hardware/runtime compatibility source-backed with catalog/evidence/project owners rather than freezing them as generic infrastructure teaching.
- Link Agent Operations `cost-and-resource-budgets/` for agent-side request/budget/lease/admission/cleanup responsibility and link generic AI Engineering reliability/cost/capacity owners for reusable mechanisms rather than duplicating them here.

## Validation

- Desired/observed resource state and provider/local evidence remain authoritative independently from worker/model narratives.
- Task completion, stopped compute, durable artifacts, retained-child cleanup, lease release, and billing/data-retention closure are distinct states where applicable.
- Ambiguous create/terminate outcomes are reconciled before retrying consequential operations.
- Liveness is never presented as sufficient workload readiness.
- Leases include fencing when stale concurrent controllers can act.
- Teardown verifies required artifacts and retained child resources before declaring closure.
- Provider-specific mutable facts remain source-backed rather than generic timeless claims.
