# Documentation Requirements

## Requirements

- Present Prompting and Instruction Design as practitioner-facing teaching for deliberately shaping model behavior through goals, instructions, context, examples, output contracts, and evaluation rather than as a universal recipe.
- Keep canonical Prompting, Few-Shot Prompting, Structured Output, and System Prompts semantics with their concept owners; this subtree teaches transferable design and verification practice.
- Materialize and link the selected children `prompt-structure/`, `examples-and-few-shot/`, `structured-outputs/`, and `prompt-debugging-and-evaluation/` because each has source-backed material ready for migration.
- Teach prompt design around explicit goals and acceptance criteria, task-relevant context, clear instruction/source boundaries, intentional output contracts, evidence/uncertainty boundaries, and representative evaluation.
- Route complex work to staged workflow/agent structures when decomposition, tools, state, validation, or recovery are required; prompting alone is not a substitute for workflow control.
- Keep provider-specific schema subsets, hidden platform context, mutable model behavior, current limits, and product features with current catalog/evidence owners.
- Treat important prompts and example sets as behavior-affecting configuration that should be regression-checked after material model, provider, context-construction, or prompt changes.

## Validation

- The subtree does not present one prompt formula as universally optimal.
- Prompting practice does not replace permissions, tools, state management, or independent validation.
- Current navigation exposes all four materialized selected children.
- Mutable provider/model behavior remains source-backed rather than timeless learning truth.
