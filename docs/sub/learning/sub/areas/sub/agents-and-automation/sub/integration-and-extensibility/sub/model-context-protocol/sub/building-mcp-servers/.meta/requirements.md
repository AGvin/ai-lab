# Documentation Requirements

## Requirements

- Use the reader-facing title `Building MCP Servers` and preserve the source tutorial's first-principles progression: decide whether MCP is appropriate, define a server contract, build a local read capability, add a resource and prompt, add a controlled mutation, validate and test failures/security, then prepare for remote deployment/authorization/versioning.
- State learning objectives explicitly: choose MCP versus Agent Skill/local function/conventional API/Plugin; choose tools/resources/prompts; build/run local stdio; validate input and useful errors; add explicit writes; test capability discovery/failure behavior; and prepare remote operation.
- Preserve the abstraction-choice table/mental model: reusable procedure without new external capability -> Agent Skill; deterministic local operation -> function/tool; ordinary non-AI service integration -> conventional API; platform-specific extension bundle -> Plugin; shared AI-facing tools/resources/prompts -> MCP server. Explain that MCP often wraps an existing API and does not replace its business logic or authorization.
- Require a pre-code server contract including server name/users/transport/capabilities/filesystem/network/credentials/failure/logging plus per-capability invoker, input, returned data, side effects, authorization, timeout, idempotency, and audit evidence.
- Use a small `project-status` example with Python and the official MCP Python SDK as a worked example, but mark concrete SDK setup/API calls as freshness-sensitive and source them from current official docs before rendering/updating.
- Preserve the minimal project layout and environment expectations from the source guide, including an isolated Python environment, `server.py`, tests, and README. Do not turn current package-manager commands or minimum Python/SDK versions into unsourced timeless facts.
- Include an equivalent minimal FastMCP tool example that reads a configured `PROJECT_ROOT`, resolves/validates the root, reports project name/path/README/Git presence, and runs over stdio. Explain that tool schemas can be derived from function signatures/docstrings and that precise descriptions matter to hosts/models/users.
- Include a conceptual host configuration example using absolute paths and environment variables; keep exact host syntax platform-owned/current-source-backed.
- Explicitly teach that stdio protocol stdout must remain protocol-only. Ordinary logs/debug output go to stderr or a file; demonstrate the difference and explain how stray stdout corrupts JSON-RPC transport.
- Preserve the resource example that exposes a controlled project configuration document and the safe path-containment pattern that resolves a candidate path and rejects escapes from the configured project root. Include symlink/path-escape considerations in security tests.
- Preserve the prompt example that combines the server's resource and status tool and separates observed facts from recommendations. Explain that prompts do not grant capabilities; client/host policy still controls access.
- Preserve the controlled mutation example: `set_project_note` previews without writing until an explicit confirmation field is true, refuses silent overwrite of an existing target, writes only under the project root, and returns observable write evidence. Explain that this field is defense in depth, not a replacement for host approval/backend authorization.
- For production mutations, teach authenticated identity, role/scope checks, idempotency keys, optimistic concurrency, transaction boundaries, audit records, rollback/compensation, and post-write verification.
- Preserve narrow input/output validation through an equivalent bounded text-file reader: contain the path, require a file, bound payload size, and reject oversized/ambiguous input before backend access. Prohibit returning secrets, unrestricted environment dumps, raw database errors, and oversized payloads by default.
- Teach actionable error categories that distinguish invalid input, denied authorization, missing resources, dependency unavailable, timeout, conflict/duplicate, and internal failure. Detailed diagnostics belong in protected logs under a correlation ID; clients get sanitized category/next action. Never convert failures into plausible success prose.
- Preserve two test layers: direct business-function tests using temporary directories/environment injection, then MCP protocol/client/inspector tests for initialization/version negotiation, capability listing, schemas/descriptions, read calls, malformed/denied input, mutation preview, confirmed sandbox write, duplicate/rollback, shutdown/restart.
- Preserve security test coverage: `../` traversal, symlink escape, oversized I/O, malformed encoding, missing/over-scoped credentials, prompt injection in resource data, repeated mutations, concurrent updates, timeout/cancellation, and secret leakage in logs/errors. Treat server-provided descriptions/annotations as untrusted unless the server itself is trusted.
- Teach transport progression: stdio for host-owned local process; Streamable HTTP for managed remote service. When moving remote, require TLS, real user authentication, audience/scope validation, tenant isolation, rate limits, request-size limits, secure session identifiers, origin/redirect controls, centralized logs/metrics, and health checks. State explicitly that an MCP session identifier is not authentication.
- Preserve versioning/compatibility guidance across server implementation, capability schemas, backend dependencies, supported MCP protocol versions, and authorization policy. Treat renamed/removed capabilities, new required args/credentials, broader write scope, changed output shape, or resource-URI semantics as potentially breaking.
- Preserve the production checklist for abstraction fit, clear capability ownership/descriptions, narrow schemas, least privilege, clean stdio, sanitized errors, protocol/business/security/failure tests, transport/auth fit, and documented version/rollback/operations.
- Cross-link `using-mcp/`, the MCP learning root, abstract concept, and formal specification. Keep normative protocol requirements specification-owned and current SDK syntax source-backed.

## Validation

- The tutorial retains a runnable conceptual progression and not merely a list of MCP terms.
- Read and write behavior, path containment, stdio discipline, auth, idempotency, security tests, error semantics, and deployment boundaries are all explicit.
- Current SDK syntax/version claims are freshness-bound rather than silently canonicalized.
- The tutorial does not imply MCP replaces backend authorization, transactions, or business validation.
