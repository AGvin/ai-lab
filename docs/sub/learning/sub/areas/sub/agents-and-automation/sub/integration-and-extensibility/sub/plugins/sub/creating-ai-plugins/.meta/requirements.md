# Documentation Requirements

## Requirements

- Use the reader-facing title `Creating AI Plugins` and preserve the source tutorial's central lesson: build a host-specific plugin only when a standalone portable skill is insufficient, keep portable behavior separate from host adapters, and test installation/runtime/update/removal as part of the plugin contract.
- State learning objectives covering necessity/host choice, portable-versus-host-specific separation, manifest/package design, bundled skills/commands/hooks/MCP safety, install/activation/update/removal tests, and marketplace publication without claiming one universal plugin format.
- Require the target host and official current schema first: target host, minimum supported version, manifest format, supported components, marketplace/direct-install mechanism, permission model, and update mechanism. Never start from an imagined generic plugin directory.
- Preserve the justification test: standalone skill for one portable procedure; plugin when several skills need joint install/versioning, custom host commands/agents, lifecycle hooks, MCP/connectors, marketplace-managed updates, namespacing, or host-specific UI/metadata.
- Preserve a recommended source architecture that separates portable `skills/` from host-specific `adapters/` (for example Claude Code/OpenAI/Cursor/OpenCode), plus optional MCP servers, tests, and repository documentation. State that portable skill sources remain canonical and adapters package them according to each host.
- Require a pre-manifest plugin contract covering plugin name/users/problems, bundled skills/commands/agents, hooks/events, MCP/connectors, runtimes, credentials, filesystem/network access, consequential actions, approval points, update/rollback, and uninstall cleanup.
- Teach building the minimum valid package first, with only the selected host's required manifest/files and a simple skill/documentation component. Validate install before adding hooks, code, or external integrations.
- Explain common manifest responsibilities conceptually: stable ID, display name/description, version, publisher/source, license, minimum host version, component entrypoints, requested capabilities/dependencies, marketplace metadata. Keep it declarative and do not hide undocumented install behavior.
- Preserve a complete host-specific worked example using Claude Code or an equivalently well-documented current host, while clearly labeling it as one adapter rather than universal syntax. The example should show the current official manifest path, skills, command, hook configuration, a small validation script, and README structure after verifying current official docs.
- Preserve the example's architectural lesson: essential skill workflow stays in portable `SKILL.md`; a host command is an adapter convenience; a hook executes at a host event and therefore has a stronger execution/safety boundary; scripts should fail visibly and document preconditions.
- For bundled MCP, require documentation of command/URL, transport, environment variables, authentication scopes, exposed tools/resources/prompts, write effects, startup/shutdown, and version pinning. Never embed production secrets in the plugin repository.
- Treat hooks as the highest-scrutiny component because they can run without explicit skill invocation. For each hook require event, matcher, handler/command, inputs, files/services accessed, failure result, timeout, diagnostics, and disable procedure. Prefer read-only validation hooks and explicit approval for external writes/destructive actions.
- Preserve independent local test layers: package validation; clean-profile installation/idempotency/unsupported-version behavior; skills/commands positive/negative discovery and namespace/resource resolution; hooks/MCP permission/timeouts/dependency/startup/shutdown/no-unexpected-access; removal/rollback including disappearance of every registered component and separate credential revocation.
- Preserve marketplace-publication guidance: separate host-required marketplace index/metadata where applicable; plugin identifier/display/version/source/package/description/categories/license/compatibility/publisher/changelog/security contact/install/removal information; never silently redirect an existing identity to an unrelated package.
- Preserve semantic-versioning-as-behavior guidance: patch for compatible clarification/fix without privilege expansion; minor for compatible optional capability; major for activation/removal/dependency/privilege/manifest incompatibility changes. Treat instruction changes as behavioral changes even when only Markdown changes.
- Preserve multi-platform publication strategy: dedicated adapter per host, validate official schema, clean install/uninstall, document unsupported components, publish host-specific version, synchronize shared skills through generation or explicit release process. Portable skills do not make a plugin package universal.
- Preserve common mistakes and fixes: copying one host manifest to another; putting essential workflow rules only in plugin metadata; adding hooks before basic package validation; auto-updating privileged plugins without review; uninstalling without credential cleanup.
- Preserve the publication checklist covering plugin necessity, host/version, portable/adapter separation, manifest validation, component inventory, permissions/approvals, clean install/update/rollback/uninstall, behavior-aware version/changelog, real publisher/source, and security contact/reporting.
- Cross-link the Plugins learning root, using tutorial, Agent Skills creation, MCP learning, and formal/current host documentation. Exact manifest fields/files/commands remain specification/platform-owned and freshness-bound.

## Validation

- The tutorial remains architecture-first and multi-platform-aware rather than teaching one vendor manifest as the definition of a plugin.
- Portable skills and host adapters have explicit ownership boundaries.
- Hooks, MCP, code, permissions, credentials, updates, rollback, and uninstall are treated as operational/security concerns, not packaging afterthoughts.
- Host-specific worked examples are verified against current official documentation before reader-facing rendering/update.
