# Documentation Requirements

## Requirements

- Present Operations and Control as the Agents and Automation learning group for operating agent systems after design: observability, safe retry/idempotency, failure recovery, runtime human intervention, and bounded token/tool/compute/time/resource consumption.
- Keep broader application/infrastructure lifecycle, fleet/resource provisioning, hosting, and provider capacity operations with AI Engineering; this group teaches how agent loops consume and govern those capabilities rather than owning all infrastructure mechanics.
- Keep reusable reliability/idempotency/retry/cost/capacity semantics with their canonical concept/AI-engineering owners and teach their agent-specific operational application here.
- Explain that the current materialized subset focuses on `cost-and-resource-budgets/` because resource-lifecycle legacy material contains source-backed agent budget/admission/lifetime/control teaching and framework provenance ready for migration.
- Do not imply that unmaterialized selected siblings `observability-and-tracing/`, `idempotency-and-retries/`, `failure-recovery/`, or `runtime-human-intervention/` are absent from the logical architecture; standard navigation reflects only physical children.
- Treat operational state, budgets, leases, approvals, resource records, and external effects as explicit authoritative control data rather than model-generated prose or conversational memory.
- Keep concrete provider/platform APIs, prices, quotas, resource types, compatibility, traces, and project-specific policies source-backed with catalog/evidence/project owners.

## Validation

- Agent operations is distinguished from broad infrastructure lifecycle and from reusable generic reliability/cost concepts.
- Operational authority remains explicit and is not delegated implicitly to model text.
- Current navigation exposes only materialized selected children.
- Mutable provider/framework behavior remains source-backed rather than timeless learning truth.
