# Documentation Requirements

## Requirements

- Use the reader-facing title `Using MCP` and preserve the legacy guide's complete learning outcome: a reader with basic command-line/configuration knowledge can select, configure, verify, operate, update, troubleshoot, and remove an MCP server safely.
- Start from the required capability rather than server popularity. Give readers a reusable pre-selection worksheet covering user goal, required tools/resources/prompts, read-only versus write access, local/remote data, credentials, and consequences of failure; recommend the smallest server and permission set that satisfies the goal.
- Teach the two major connection/deployment models used by the source guide: local stdio servers launched as child processes and remote Streamable HTTP servers. Explain practical selection criteria for each and state that remote operation is not automatically safer.
- Before connection, require an inventory of server identity/source/version, transport, command or URL, authentication, exposed tools/resources/prompts, filesystem/network access, write effects, telemetry/logging, update process, and removal procedure. Include source/dependency/install-script/container/environment/outbound-connection review proportional to risk.
- Include a conceptual local-host configuration example showing a command, arguments, and environment variables. Teach absolute executable/script paths, version pinning, secret separation, narrow working directories, read-only mounts where possible, and low-privilege execution. Make clear that exact host configuration syntax is mutable/platform-specific.
- Include a conceptual remote-server configuration example and teach scoped/short-lived credentials where supported, TLS/certificate checks, redirects, tenant identity, token storage, and private-network/callback exposure. Keep current authentication details sourced from official documentation.
- After connection, require capability discovery before use: inspect tool names/descriptions/input schemas, resource URI patterns/types, prompt names/arguments, implementation/protocol version, optional capabilities, and notifications. Do not assume marketing copy describes the whole exposed surface; disable/deny unnecessary capabilities where the host supports it.
- Preserve the staged verification sequence: disposable session -> list capabilities -> harmless read-only tool -> non-sensitive resource -> verify result/logs -> deny a permission and observe failure -> only then test writes in a sandbox/test account.
- For consequential tools, require readers to identify the exact side effect, affected account/environment, reversibility, approval requirement, idempotency strategy, post-execution verification, and rollback/compensation. Explain that a host approval dialog alone is insufficient; tool schema/description, server authorization, backend policy, and user approval should align.
- Teach prompt-injection handling for MCP resources and tool results as untrusted external data: do not execute returned instructions automatically; separate data/instructions; validate URLs, paths, and identifiers; avoid secrets in errors; require explicit approval for effects derived from retrieved content.
- Teach secret/authentication hygiene: purpose/environment-scoped credentials, no committed tokens, no long-lived secrets in process arguments, no shared personal admin credentials, no environment dumps in logs, and explicit rotation/revocation after compromise or removal.
- Teach observability that captures connection/protocol/server version, capability changes, tool name/duration/status/correlation ID, approval decision, sanitized error category, retry/timeout, and side-effect identifier while excluding tokens, complete customer records, confidential documents, and unrestricted arguments by default.
- Preserve the update workflow: record current version/capabilities, inspect release notes/source diff, compare schemas/permissions, test against fixtures, verify auth/transport compatibility, retain rollback, and stage deployment for shared services. Explain that schema/resource-scope changes can break behavior even when startup succeeds.
- Preserve removal guidance: disable/remove host configuration, reload host, verify capabilities disappear, stop/remove local processes/containers, review generated files before deletion, revoke tokens/OAuth grants, remove firewall/tunnel/service-account changes, and retain sanitized audit records according to policy.
- Preserve troubleshooting sections for: server not starting; connected but no tools; timeouts; works in one client but not another; repeated writes creating duplicates. Route each symptom through concrete checks such as paths/runtime/dependencies/env/stdio contamination, initialization/capability negotiation/version/policy, backend/host timeout/deadlock/interactive input, transport/auth/optional capability/client configuration, and idempotency keys/lookup-before-create.
- Preserve an operational checklist covering capability-first selection, source/version/dependency review, capability/permission inventory, secret storage, read-before-write testing, approvals/backend authorization, prompt-injection handling, sanitized logs, and tested update/rollback/disable/revocation.
- Cross-link the MCP learning root and the `building-mcp-servers/` continuation. Keep formal protocol language specification-owned and concrete host/server facts freshness-bound and sourced.

## Validation

- The guide is usable without knowing one specific host's exact UI or config schema.
- It covers the full select -> inspect -> configure -> discover -> stage-test -> operate -> update -> remove lifecycle from the preserved source.
- Write-capable tools are never normalized as harmless and prompt-injection/secret/idempotency boundaries remain explicit.
- Mutable host syntax/support is not presented as timeless canonical fact.
