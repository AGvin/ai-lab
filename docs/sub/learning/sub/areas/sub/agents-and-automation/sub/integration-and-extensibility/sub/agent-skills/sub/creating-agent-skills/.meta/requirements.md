# Documentation Requirements

## Requirements

- Use the reader-facing title `Creating Agent Skills` and preserve the source tutorial's goal: teach a reader with no prior skill-authoring experience to design, implement, test, version, and publish a reusable, inspectable skill with explicit triggers, boundaries, failure behavior, portability, and safety.
- State learning objectives covering abstraction choice; a valid current skill directory/entrypoint; discovery metadata; separation of core instructions from references/scripts/assets; approval/failure design; discovery/activation/execution/portability testing; and safe version/publication.
- Preserve the abstraction-choice guidance: one-off instruction -> prompt; always-on repository facts/conventions -> repository instructions; deterministic executable operation -> tool/script; standardized external AI capabilities -> MCP; host-specific installable bundle -> Plugin; reusable procedure loaded only when relevant -> Agent Skill. Explain composition rather than false mutual exclusion.
- Require a behavioral contract before files. Preserve the fields `Name`, `User problem`, `Use when`, `Do not use when`, `Required inputs`, `Expected outputs`, `Available tools`, `Side effects`, `Approval points`, `Failure behavior`, and `Success criteria`, plus the source's release-notes-style worked contract or an equivalent complete example.
- Teach the current minimum directory and entrypoint using the current Agent Skills specification as the normative source. Preserve examples of good/poor names, but make exact naming/frontmatter rules explicitly specification-sourced/freshness-bound.
- Preserve current YAML-frontmatter teaching for `name` and `description` plus optional fields such as license/compatibility/metadata only as current specification examples. Explain that host-specific extensions are adapters and must not contain the only copy of essential portable workflow behavior.
- Preserve the discovery-description lesson: contrast an overly vague output-only description with a stronger description containing task, qualifying context, natural trigger language, and important exclusions; do not move the whole workflow into discovery metadata.
- Teach an instruction body organized around when to use, required inputs, workflow, output, approvals/safety, failure handling, and references. Prefer imperative/testable steps over vague statements such as `use best practices`.
- Preserve the release-notes workflow example's important invariants: exact revision range, enumerate evidence, exclude non-user-impact noise, group by impact, mark breaking changes/migrations, source non-trivial claims, present draft, and require approval before publication.
- Teach progressive disclosure inside a skill package: keep the entrypoint focused and move large conditional material to references, deterministic/repeatedly error-prone operations to scripts, and copy/adapt output resources to assets. Preserve representative directory structure and explicit links from the entrypoint.
- For scripts, require declared runtime/dependencies, input validation, machine-readable/clearly delimited output, non-zero failure exit, no hidden network/destructive defaults, and dry-run support for consequential changes when practical.
- Preserve the three source examples as learning patterns rather than product catalog facts: (A) a minimal friendly release-notes skill with explicit input/output/safety; (B) an SFCC log-analysis skill with a separate error-classification reference and privacy redaction; (C) a repository Markdown link-checker skill with a deterministic Python script and non-modifying default behavior. Retain enough detail that readers can understand why each structure is chosen.
- Teach tool use and approvals explicitly: a skill does not grant tools; required capabilities must be declared/detected, and consequential side effects must identify operation, affected data/system, reversibility, required approval, and post-action verification. Preserve the Git-tag approval example or an equivalent concrete example.
- Teach user-invoked versus model-invoked behavior as host-dependent. Broad interview/orchestration skills are often safer as explicit invocation; narrow disciplines can be good automatic-discovery candidates. Do not claim a universal invocation field unless the current specification does.
- Preserve the client-adapter principle using an example such as optional `agents/openai.yaml`: essential workflow remains in portable `SKILL.md`, while client presentation/config lives in adapter metadata. Keep exact platform filenames/behavior source-backed.
- Preserve four test layers: structural validation; positive/negative discovery tests; execution tests against observable invariants; cross-client portability tests. Include checks for directory/entrypoint/frontmatter/references/scripts/licenses, natural positive/negative prompts, required questions/order/evidence/approvals/output/failure handling, and host differences in discovery/invocation/paths/scripts/permissions/metadata/context/output.
- Preserve common failure modes and remediations: description too broad, too vague, oversized entrypoint/handbook, unavailable-tool assumptions, scripts hiding consequential behavior, and happy-path-only testing.
- Preserve publication/versioning guidance: stable source, license, supported clients/runtime dependencies, immutable revisions/tags, behavioral changelog, instruction changes reviewed like code, upgrade testing, and no silent permission/network expansion. Explain distribution by direct copy/installer/plugin as separate mechanisms.
- Preserve the final creation checklist covering recurring procedural fit, explicit use/non-use conditions, contract fields, current spec validity, discovery tests, focused entrypoint/resources, script failure behavior, approval gates, structural/discovery/execution/failure/portability tests, and license/source/update policy.
- Cross-link `using-agent-skills/`, the Agent Skills learning root, abstract concept, formal specification, portability continuation, and plugin/MCP learning where the abstraction comparison requires it.

## Validation

- The tutorial remains a full design-to-publication learning sequence, not only a `SKILL.md` syntax reference.
- Normative schema/layout facts are clearly sourced from the current formal specification.
- Portable behavior remains separate from host-specific adapters.
- Positive/negative discovery, execution/failure, safety approvals, scripts, portability, versioning, and update-as-behavior-change are all retained.
