# Documentation Requirements

## Requirements

- Own decision support where the reader already knows software is the class being selected.
- Keep factual software identity, licensing, capabilities, deployment, integrations, and operational facts in `catalog/software/` and link those canonical owners.
- Materialize only substantive decision leaves; do not infer a deeper software-selection taxonomy for symmetry.
- Support cross-category software decisions when the adoption question legitimately compares different software classes.

## Validation

- The root does not mirror the factual `catalog/software/` taxonomy.
- Each child is a real reader decision rather than an empty category placeholder.
- Recommendation claims expose assumptions, trade-offs, and re-evaluation boundaries.
