# Documentation Requirements

## Requirements

- Define software-development model selection by concrete task rather than a universal coding ranking.
- Cover the selected task families: generation/editing, understanding, debugging/repair, testing, review, security engineering, architecture, agentic software engineering, and development/reliability analysis.
- Preserve the useful legacy coding decision rule: start with the least expensive credible route that meets the required acceptance tier and escalate on repeated capability failures or unacceptable review/regression cost.
- Require evaluation of correctness, omissions, repository understanding, tool use, recovery, verification, retries, review effort, and cost per accepted result.
- Preserve the representative evaluation minimum from the legacy coding guide.
- Preserve useful concrete candidate hypotheses from the legacy coding guide only after current first-party identity/capability verification; present them as candidates to evaluate for bounded assignments, not as a copied rank order or universal recommendation.
- Add newly canonicalized models to the candidate set only after a documentation-impact review shows that they materially change an existing software-development shortlist or evaluation route.
- Include Kimi K3 as a capability-first evaluation candidate for long-horizon coding, large-repository work, terminal/tool-driven engineering, visual-in-the-loop development, and agentic software-engineering assignments where its provider-documented 1M-token context and long-horizon coding/tool-orchestration capabilities materially expand the route set.
- Treat Kimi K3 coding benchmarks and autonomous engineering case studies as provider evidence rather than independent AI Lab proof of correctness, maintainability, safe tool use, or accepted-result superiority; evaluate on the target repository/scaffold with explicit verification and retry bounds.
- Keep Kimi K3's 2.8T total / 104B active MoE scale, open-weight distribution, and custom license as canonical reference facts; do not infer practical self-hosting, cost, latency, or memory fit from active parameters, and recheck hosted Kimi API/Kimi Code availability, prices, limits, and reasoning controls at decision time.
- Include Qwen3-Coder 30B-A3B Instruct as a current self-hostable coding/agentic-coding evaluation candidate: preserve its provider-documented 30.5B-total/3.3B-active MoE scale, 262,144-token native context, non-thinking-only mode, and agentic-coding/tool-use positioning only through the canonical reference link; do not infer memory fit or independent task quality from active parameters or provider claims.
- Keep Qwen3-Coder 30B-A3B Instruct distinct from Qwen3-Coder-Next: evaluate the 30B-A3B model as a smaller MoE coding-agent route and Coder-Next as a different 80B-total/3B-active architecture rather than assuming one supersedes the other without workload evidence.
- Keep legacy compact/local coding baselines distinguishable from current agentic or hosted candidates so older but still available models can remain reproducible comparison baselines without being presented as current winners.
- For candidate entries, state the intended evaluation role and the material limitation or evidence boundary that determines escalation.
- Treat provider positioning and benchmark claims as provider-documented evidence, not independent AI Lab proof of task superiority.
- Treat tool/function-calling availability as runtime or hosted-surface dependent when official sources distinguish model capability from a deployment surface.
- Recheck mutable hosted availability, aliases, prices, limits, and provider features at decision time rather than copying them into a durable candidate ranking.
- Link canonical model facts from `../../../../../reference/` and keep task findings in selection.
- Materialize more specific selected child nodes only when their shortlist, evaluation dimensions, or acceptance criteria materially differ.

## Validation

- The page contains no universal best coding model claim.
- Dated legacy quick-pick order is not copied forward as a current ranking.
- Useful legacy candidate hypotheses are not discarded merely because they were embedded in legacy model-reference pages or comparison tables.
- Every retained candidate is framed as an evaluation starting point with a task scope and limitation rather than as verified superiority without AI Lab evidence.
- Kimi K3 provider benchmarks/case studies are not treated as independent repository-level correctness or complete-loop evidence, and its active-parameter count is not treated as local memory-fit evidence.
- Qwen3-Coder 30B-A3B Instruct is represented as a distinct coding-model candidate and is not conflated with Qwen3-Coder-Next or reduced to its active-parameter count.
- Model facts remain owned by canonical reference nodes.
