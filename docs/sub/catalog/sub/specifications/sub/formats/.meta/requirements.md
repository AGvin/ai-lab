# Documentation Requirements

## Requirements

- Present Formats as the specification group for identifiable formal file, serialization, graph-exchange, model-artifact, agent-readable-document, and related data-format contracts whose normative identity belongs in the catalog.
- Create one canonical child per concrete selected format/proposal artifact; do not create generic wrapper artifacts that duplicate concept or learning groupings.
- For each concrete format, preserve authoritative specification/proposal identity, current status, version/freshness boundaries, structure, normative fields/types/encoding rules, and conformance/compatibility semantics only to the depth supported by the upstream source.
- Keep practical choosing, authoring, converting, validating, or deployment guidance with concepts/learning or concrete product owners; keep dated performance/quality findings with evidence/decision owners.
- Preserve maturity/status precisely. Placement under `catalog/specifications/` means the node is a specification-class artifact; it does not upgrade a proposal or emerging convention into a ratified standard. In particular, `llms-txt/` must remain labeled according to current llmstxt.org proposal status.
- Keep concrete child identity and normative details with each child profile rather than duplicating them in this category index.
- Render standard direct-child navigation from only currently materialized concrete format nodes when rendering is activated.

## Validation

- The group is not used for generic format pedagogy, runtime compatibility matrices, or implementation tutorials.
- Concrete format/proposal nodes cite authoritative/upstream sources for normative claims and status.
- Proposal-class artifacts are not mislabeled as ratified standards.
- Current navigation exposes only materialized children and does not imply that unmaterialized formats are absent from the selected architecture.
