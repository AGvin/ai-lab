# Documentation Requirements

## Requirements

- Present Model Context Protocol (MCP) as a versioned formal interoperability protocol whose normative requirements are defined by the current first-party specification and versioned schema, not by host/product behavior or legacy AI Lab prose.
- Record the current verified specification boundary explicitly: on 2026-09-02 the latest released revision is `2026-07-28`. Re-check the official specification/repository before updating exact methods, fields, headers, capabilities, errors, transport rules, authorization behavior, extensions, or deprecations.
- Treat the first-party versioned specification text and schema as the authority for RFC-style `MUST` / `SHOULD` / `MAY` requirements; use implementation docs and SDK behavior only as implementation evidence, not as a substitute for protocol truth.
- Define the modern `2026-07-28` core as JSON-RPC 2.0 with stateless, self-contained client requests. Every modern request carries the protocol version and client capabilities in `_meta`; do not restore the former required `initialize` / `notifications/initialized` handshake or protocol-level session model as current semantics.
- Preserve the current version-selection contract: servers implement `server/discover`; clients may call it before other requests for supported versions/capabilities/identity, or send a request directly and handle `UnsupportedProtocolVersionError`. Backward compatibility with initialization-based `2025-11-25` and earlier revisions remains a separate, explicitly versioned compatibility path.
- Preserve the modern message-direction boundary from the current transport specification: clients send requests/notifications; servers send responses/notifications. Server needs for additional client input use the current Multi Round-Trip Request pattern (`InputRequiredResult`, `inputRequests`, retry with `inputResponses`) rather than new server-initiated JSON-RPC requests.
- Preserve the current core server feature vocabulary at the specification level: Resources, Prompts, and Tools. Preserve current client-side capability/feature vocabulary only as defined by the active revision, and reflect deprecations rather than presenting historical features as recommended new design.
- Record current deprecation state from the active specification: Roots, Sampling, and Logging are deprecated for new implementations; legacy HTTP+SSE is deprecated in favor of Streamable HTTP; Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents while retained for backward compatibility. Re-check the deprecated-feature registry before changing these claims.
- Keep optional extensions distinct from the core protocol. Extensions are explicitly identified and capability-advertised; each extension owns its own settings/fallback contract. Do not promote experimental or extension-specific methods into core MCP requirements.
- Preserve the standard transport-binding boundary: the current specification defines stdio and Streamable HTTP, while permitting custom transports that preserve the JSON-RPC message format, message patterns, and per-request metadata model. Protocol meaning stays transport-independent; each binding owns framing/delivery/cancellation details.
- For Streamable HTTP, treat the JSON-RPC body/per-request `_meta` as protocol truth and HTTP headers as the transport-defined mirror/routing surface where required. Source exact required header names, mismatch behavior, response framing, cancellation, and backward-compatibility detection from the active Streamable HTTP specification rather than from product examples.
- Preserve the current authorization applicability boundary: MCP authorization is optional overall; when supported on HTTP-based transports, implementations should conform to the MCP authorization specification, while stdio implementations should use environment-supplied credentials rather than applying the HTTP authorization flow.
- Keep current HTTP authorization rules source-backed to the active specification, including Protected Resource Metadata discovery, authorization-server discovery, client registration choice, issuer/credential isolation, least-privilege scope handling, and applicable OAuth/OIDC standards. Do not copy a point-in-time OAuth flow into timeless prose without a revision/freshness boundary.
- Keep schema-level details such as exact JSON-RPC methods, request/result structures, `_meta` keys, required `resultType`, cache hints, error-code allocation, and capability objects aligned to the versioned first-party schema; avoid duplicating large enums or method inventories when a source reference is more durable.
- Keep conceptual identity, architecture interpretation, trust-boundary explanation, and relationship to Tool Calling / Agent Skills / Plugins with the canonical MCP concept owner; keep using/building/debugging/operations/security pedagogy with the selected MCP learning subtree.
- Keep concrete MCP clients, hosts, servers, SDKs, registries, provider support matrices, implementation bugs, security advisories, deployment configurations, and mutable version/support facts with their applicable catalog/software/service/evidence owners.

## Validation

- Current MCP requirements do not describe `initialize` or protocol-level sessions as mandatory for revision `2026-07-28`.
- Exact normative statements are traceable to the current official MCP specification/schema and carry a visible revision boundary where they may change.
- Historical compatibility behavior is labeled as legacy/dual-era behavior rather than blended into the modern core.
- Deprecated features are not recommended for new implementations merely because they remain supported during the deprecation window.
- This specification node does not become an MCP tutorial, SDK guide, product-support matrix, or generic integration concept page.
