# Documentation Requirements

## Requirements

- Present `hardware/` as the factual catalog owner for identifiable hardware products and product families with durable practical value for AI training, inference, evaluation, data processing, or related workloads.
- Keep concrete hardware identity distinct from processor/GPU architecture concepts, complete server/system platforms, hosted cloud services, driver/runtime software, and deployment recommendations.
- Preserve exact product/SKU boundaries. Memory capacity, bandwidth, supported numeric formats, interconnects, form factors, virtualization/partitioning, power envelopes, host requirements, and support status may differ between variants and must be source-backed at the applicable product/form-factor level.
- Treat availability, support lifecycle, driver/runtime compatibility, cloud availability, pricing, benchmark performance, and software-stack support as mutable facts requiring current verification.
- Do not generalize vendor marketing comparisons into cross-vendor performance conclusions without matched independent evidence and workload conditions.
- Materialize concrete children only when their AI relevance and source-backed identity justify durable catalog coverage; do not pre-create vendor, accelerator-type, architecture, or generation branches merely for symmetry.
- Render the standard direct-child navigation from the validated materialized child projection.

## Validation

- Every child represents an identifiable hardware product/family rather than a generic architecture concept, cloud instance, software runtime, or unqualified recommendation.
- Product-family statements do not erase materially different SKU/form-factor specifications.
- Mutable support/availability/performance claims are time-scoped and source-backed when present.
- Navigation exposes only materialized hardware and does not imply that the initial set is exhaustive.
