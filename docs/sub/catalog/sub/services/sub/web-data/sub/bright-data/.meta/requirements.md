# Documentation Requirements

## Requirements

- Catalog Bright Data as a vendor-operated managed web-access, extraction and browser-data platform. Its released Web Scraper APIs, SERP API, Web Unlocker, and Browser API have distinct modes: structured managed data feeds, search-engine results, single-request access and full multi-step managed browser sessions; preserve these without cloning a new owner per endpoint.
- Place the primary platform under web-data because its product portfolio centers on web retrieval and datasets; clarify that Browser API offers hosted Playwright/Puppeteer/Selenium automation, which is not identical to results-oriented scrape/search API execution.
- Distinguish prebuilt Bright Data-managed scraping endpoints and configurable Studio scrapers from custom agents/third-party target websites. Do not imply that captured source content, target-site intellectual property, or third-party consumer data belongs to Bright Data.
- Respect source/site terms, privacy and personal-data collection rules and applicable access controls. Vendor statements about compliance, CAPTCHA bypass and success rates are not authorization for indiscriminate scraping or proof of universal legal access.
- Treat scraper target coverage, proxies, geographic restrictions, pricing, concurrency, response formats, region availability, access controls and product API boundaries as freshness-sensitive and tier-dependent.
- Keep vendor-published comparison rankings distinct from independently reproducible benchmarking. Preserve exact producer relation.

## Validation

- Published first-party documentation demonstrates a live publicly documented hosted service rather than roadmap-only capability.
- Scope/feature maturity and site/data access limits are source-backed and not overgeneralized.
- Exact `produced-by` relation has an inverse `produces` link in the named vendor producer.
