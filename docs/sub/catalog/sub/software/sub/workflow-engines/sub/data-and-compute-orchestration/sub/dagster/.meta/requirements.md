# Documentation Requirements

## Requirements

- Identify Dagster as an open-source data orchestrator for building, testing, observing, and operating data pipelines and data assets.
- Preserve its primary placement under `workflow-engines/data-and-compute-orchestration`; software-defined assets, lineage, and observability are central orchestration concepts rather than separate catalog products.
- Preserve Elementl, Inc. d/b/a Dagster Labs as the company behind the Dagster open-source project while keeping Dagster software and Dagster+ as distinct product/service layers.
- Preserve the July 2026 Prefect acquisition transition as current lifecycle context. Current first-party surfaces use both completed-acquisition and pending-close wording, so do not materialize an `owned-by` relation until authoritative current sources unambiguously confirm the legal close/ownership state.
- Distinguish open-source Dagster software from Dagster Plus and other managed commercial services.
- Render the standard `entity-relations` block from the validated current-entity relation projection.
- Keep asset/automation APIs, integrations, deployment architecture, managed-service features, acquisition-transition details, and other mutable implementation facts source-backed when expanded.
- Include current official Dagster documentation, repository, legal/company identity, and acquisition-transition references.

- Elementl/Dagster Labs, Dagster OSS, and Dagster+ are not conflated.
- The Prefect acquisition transition is not converted into an unsupported canonical ownership edge while first-party close-status wording remains inconsistent.
- Open-source and managed service boundaries are not conflated.
