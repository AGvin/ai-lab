# Documentation Requirements

## Requirements

- Use the reader-facing title `AI Security and Resilience` and introduce `security and resilience` as the shorter domain term.
- Define AI security as protecting AI-enabled systems, their models/data/context/tools/infrastructure, and affected assets against adversarial actions or unauthorized access/use/modification/disclosure/disruption, while resilience covers the ability to continue, degrade safely, recover, and adapt when attacks, compromise, faults, or dependency failures occur.
- Keep the domain system-level and lifecycle-wide. Security properties can depend on data collection/training, model supply chain, adaptation, prompt/context handling, retrieval, tools, APIs, output handling, deployment, monitoring, updates, incident response, and retirement rather than the base model alone.
- Distinguish AI-specific security from generic cybersecurity without isolating them. Conventional controls for identity, authentication, authorization, secrets, network/application security, software supply chain, patching, logging, and incident response remain applicable, while AI introduces additional model/data/prompt/retrieval/tool attack surfaces and probabilistic behavior.
- Distinguish security from safety. Security focuses on adversarial/unauthorized manipulation, access, misuse, compromise, or disruption; safety focuses on avoiding unacceptable harms and hazardous behavior whether or not an attacker is present. One incident can implicate both domains.
- Distinguish security from privacy. Security controls can protect confidentiality and prevent unauthorized disclosure, while `privacy/` owns broader collection/use/minimization/consent/inference and privacy-risk semantics. A secure system can still violate privacy policy, and a privacy-preserving design can still have security weaknesses.
- Distinguish security from information integrity. `information-integrity/` owns provenance, support, grounding, citation, source/context fidelity, and trustworthy interpretation. Security attacks such as poisoning or prompt injection can undermine information integrity, but the domains are not interchangeable.
- Distinguish resilience from ordinary reliability. `ai-engineering/reliability-and-resilience/` owns engineering mechanisms for retries, idempotency, failure recovery, and operational continuity; trustworthy-AI security/resilience owns adversarial threat resistance, containment, compromise recovery, and evidence that security properties survive attack or degradation.
- Explain threat modeling as context-specific. Identify protected assets, trust boundaries, adversaries, capabilities/access, attack surfaces, goals, preconditions, affected users/systems, consequence severity, and assumptions before selecting controls or evaluating residual risk.
- Treat attacker capability as multi-dimensional. Query access, source/resource control, training-data control, model/artifact access, tool/API access, insider privileges, physical/infrastructure access, and supply-chain influence enable different attacks and should not be collapsed into a single `attacker` category.
- Explain attack lifecycle/location. Threats can target training/pretraining data, fine-tuning/adaptation, model artifacts, dependencies, deployment infrastructure, inference queries/prompts, retrieved/resources, tools, outputs, monitoring, or downstream consumers.
- Cover confidentiality, integrity, availability, authorization/agency, abuse/misuse, and recovery impacts as related dimensions rather than one universal attack objective. Security evaluation should state which assets/properties the attack threatens.
- Explain defense in depth. Model alignment/instruction hierarchy, content filtering, trusted parsing, isolation, least privilege, sandboxing, access control, secrets management, schema/output validation, approval gates, monitoring, anomaly detection, rate/capacity controls, provenance, rollback, and incident response address different layers and none is a universal substitute for the others.
- Treat model outputs as untrusted inputs to downstream components unless independently validated for that interface. A fluent or apparently compliant response must not directly gain shell/database/network/browser/file-system/financial or other privileged authority without deterministic controls.
- Treat retrieved/tool/external content as untrusted with respect to control authority even when it is useful data or evidence. Source relevance/internal indexing does not grant permission to override system policy, expose secrets, or invoke privileged actions.
- Keep secrets and credentials outside unnecessary model-visible context. System prompts, retrieval results, logs, tool outputs, environment variables, tokens, credentials, private keys, and sensitive records require deterministic access/minimization controls rather than relying on the model not to reveal them.
- Explain least privilege as a cross-cutting security principle without materializing its still-unselected child. Each model/tool/agent/service/session/tenant should receive only the capabilities, data scopes, credentials, network access, write permissions, and duration required for its task.
- Explain trust boundaries without materializing the still-unselected `trust-boundaries/` leaf. Data/instructions crossing user, model, retrieval, tool, service, tenant, network, process, storage, provider, or human boundaries require explicit validation and authority rules.
- Explain sandboxing/isolation as a control family without materializing the still-unselected `sandboxing/` leaf. Process/container/VM/browser/tool sandboxes can reduce impact but have escape, side-channel, configuration, network, filesystem, and credential assumptions that must match the threat model.
- Explain secure supply-chain concerns at the conceptual boundary: model/checkpoint/adapters, tokenizer/processors, code, containers, dependencies, datasets, prompts/templates, plugins/tools, and downloaded artifacts can be tampered with or malicious; exact products/advisories remain concrete owners.
- Delegate adversarial manipulation of persistent learning/adaptation data to the selected `data-poisoning/` child. Keep retrieval poisoning, direct model-artifact tampering, malicious dependencies, and accidental bad data distinct from that learning/update-data attack family.
- Explain prompt injection as the selected direct `prompt-injection/` child and do not flatten its nested `indirect-prompt-injection/` specialization. Prompt injection concerns adversarial/conflicting instruction influence at inference/application time and remains distinct from poisoning of persistent learning/adaptation data.
- Delegate adversarial manipulation of external retrievable evidence or retrieval state to the selected `retrieval-poisoning/` child. Retrieval poisoning can insert, modify, remove, rank, index, or otherwise manipulate documents, records, metadata, chunks, embeddings/vector or index state, graph/knowledge entries, ranking inputs, or equivalent retrieval surfaces so later queries preferentially surface attacker-controlled or attacker-favored content without requiring model-parameter modification.
- Keep retrieval poisoning distinct from indirect prompt injection. A poisoned retrieval source can contain false or misleading evidence that changes an answer without instruction-like content; when retrieved malicious content is interpreted as instructions, the same incident can additionally realize indirect prompt injection.
- Keep adversarial retrieval poisoning distinct from ordinary information-integrity/retrieval-quality failures. Stale, contradictory, low-quality, incorrectly indexed, or corrupted content can degrade retrieval without being a poisoning attack unless an adversary intentionally creates or exploits the manipulation.
- Explain jailbreaking as related but distinct terminology without materializing its still-unselected child. Jailbreaking commonly targets bypass of model safety/alignment restrictions; prompt injection more broadly manipulates application/model instruction following and can target data/tool/system behavior.
- Explain attack detection separately from prevention. Monitoring refusals, anomalous prompts, tool calls, access patterns, outputs, index/source changes, or model behavior can help detect incidents but does not prove an attack was prevented or that no compromise occurred.
- Explain resilience through containment and recovery: limit blast radius, fail safely, preserve evidence, revoke credentials, isolate compromised components, switch to eligible fallback paths, restore known-good artifacts/data, re-index/redeploy when needed, and revalidate before full service restoration.
- Explain graceful degradation under attack. Disabling tools, narrowing data access, switching to read-only, requiring approval, rate-limiting, returning cached/verified data, or refusing a task can be safer than continuing normal operation with weakened controls.
- Treat backups/rollback as insufficient without compromise-aware recovery. Restoring poisoned data, compromised model artifacts, leaked credentials, or vulnerable dependencies can reproduce the incident; recovery requires identifying the affected trust boundary and clean state.
- Treat mitigations as conditional risk reduction, not proof of elimination. Attackers adapt, model/provider versions change, filters have false positives/negatives, and system composition can create bypasses; controls require representative adversarial testing and operational monitoring.
- Distinguish red teaming/penetration/adversarial evaluation from proof of absence. Testing can discover weaknesses and estimate control performance under tested scenarios but cannot establish that no unknown attack exists.
- Explain version/currency boundaries for security claims. Model/runtime/prompt/tool/retrieval/security-control updates can invalidate prior threat assessments and evaluations; record material versions and re-test when attack surface or privilege changes.
- Explain multi-tenant security explicitly where applicable. Shared models, accelerators, caches, indexes, tools, logs, queues, or credentials must not collapse tenant authorization/isolation merely because compute is shared.
- Explain side-effect risk. Systems that can send messages, modify files, execute code, browse authenticated sessions, purchase/transfer assets, change infrastructure, or update records require stronger deterministic authorization and approval boundaries than read-only generation.
- Keep `prompt-injection/`, `data-poisoning/`, and `retrieval-poisoning/` as the currently selected direct children. Do not infer other architecture-gap descendants such as trust boundaries, least privilege, sandboxing, secret handling, or jailbreaking until separately selected.
- Keep concrete attack payloads/incidents, CVEs/advisories, current model/provider vulnerabilities, red-team reports/results, threat models for specific systems, security configurations, credentials, security products, and incident runbooks with their applicable evidence/catalog/project owners.
- Render the standard direct-child navigation from the validated materialized child set when reader-facing rendering is activated.
- Use the canonical entity references as research inputs for trustworthy-AI secure/resilient characteristics and current adversarial-ML taxonomy when reader-facing rendering is activated.

## Validation

- AI security/resilience is not reduced to model refusal behavior, content moderation, generic cybersecurity, privacy, safety, information integrity, or engineering reliability alone.
- Threat/attacker capabilities, protected assets, lifecycle stage, attack surface, impact, and assumptions remain explicit.
- Model/retrieval/tool outputs are not treated as deterministic authorization/security boundaries.
- Defense-in-depth controls are presented as layered mitigations with residual risk rather than guaranteed prevention.
- Resilience includes containment/recovery/revalidation after attack, not only uptime or automatic retry.
- `prompt-injection/`, `data-poisoning/`, and `retrieval-poisoning/` are the currently selected direct children; other legacy security leaves are not inferred from parent terminology.
- Prompt injection, data poisoning, retrieval poisoning, accidental bad data/retrieval defects, and supply-chain/artifact compromise remain distinguishable attack/problem classes.
- Concrete incidents, vulnerabilities, payloads, products, configurations, red-team findings, and project threat models remain outside the reusable security domain owner.
- Direct-child navigation contains only currently materialized selected descendants.
