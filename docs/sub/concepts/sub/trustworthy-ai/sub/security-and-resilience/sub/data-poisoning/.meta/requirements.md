# Documentation Requirements

## Requirements

- Use the reader-facing title `Data Poisoning`.
- Define data poisoning as an adversarial-machine-learning attack family in which an attacker intentionally inserts, removes, modifies, relabels, selects, weights, or otherwise manipulates data or data-derived supervision used by a learning/adaptation process so the resulting learned model or policy acquires attacker-desired behavior, degraded utility, hidden triggers/backdoors, biased behavior, or other persistent compromise.
- Keep adversarial intent or attacker-controlled manipulation explicit. Accidental label mistakes, noisy records, duplicates, stale sources, ordinary sampling bias, natural distribution shift, or poor dataset design can damage model quality but are data-quality/generalization problems rather than poisoning unless an adversary deliberately creates or exploits the manipulation as an attack.
- Treat poisoning as a persistent learning/update-path attack rather than an inference-only prompt attack. The compromised data affects model parameters, learned representations, reward/preference models, adapters, policies, or other state produced by training/adaptation/update procedures.
- Cover pretraining, supervised fine-tuning, instruction tuning, preference/reward data, reinforcement-learning feedback, continual/online learning, personalization/adaptation, distillation data, model-generated/synthetic training data, and other persistent update inputs as possible poisoning surfaces when the concrete system uses them.
- Distinguish data poisoning from `prompt-injection/`. Prompt injection manipulates instruction following through inference/application inputs; data poisoning changes persistent learned behavior through compromised learning/adaptation data. A poisoned dataset can contain instruction-like examples, but its attack path remains learning-time poisoning.
- Distinguish data poisoning from retrieval poisoning. Retrieval poisoning manipulates documents, records, metadata, indexes, graphs, or other external knowledge used at inference without necessarily updating model parameters; it can change evidence or deliver indirect prompt injection while requiring different detection/recovery from training-data poisoning.
- Distinguish data poisoning from direct model/artifact tampering. Replacing weights, editing checkpoint tensors, modifying model files, injecting malicious code into loaders/dependencies, or distributing a trojanized binary is a model/software/supply-chain compromise even if the resulting behavior resembles a poisoned model.
- Distinguish poisoning from evaluation/test-set contamination. Manipulating or leaking evaluation data can invalidate measurement or hide a compromise; it becomes part of a poisoning/update path only when that evidence is reused to select, optimize, fine-tune, reward, or otherwise persistently alter the learned system.
- Distinguish poisoning from ordinary data leakage. Accidental train-test overlap or future-information leakage can make evaluation misleading without an adversarial poisoning objective, although an attacker can intentionally create such leakage as part of a broader attack.
- Explain targeted versus indiscriminate objectives. Targeted poisoning can alter behavior for chosen examples/classes/entities/triggers while preserving normal performance elsewhere; availability/degradation poisoning aims to reduce broad utility or make training unusable. These are variants, not automatically separate selected concepts.
- Explain backdoor/trigger poisoning as a targeted variant. A model can behave normally on ordinary inputs but exhibit attacker-chosen behavior when a trigger pattern, phrase, feature, context, or condition appears; not every poisoned model contains a backdoor.
- Explain clean-label poisoning as a variant where poisoned examples can retain plausible/correct-looking labels while manipulating features/distribution or training influence. Label flipping is common but not required by the concept.
- Do not require a large poisoning fraction. Some attacks can work through small strategically selected sets, high-leverage examples, repeated sources, influential annotators, preference pairs, triggers, or update streams; effectiveness depends on model, objective, data, training procedure, and attacker knowledge/access.
- Explain attacker capability explicitly. Possible control points include public/user-contributed data, scraped sources, data vendors, annotation/labeling pipelines, synthetic-data generators, feedback channels, preference/judge systems, ingestion/filtering logic, data stores, insiders, or compromised upstream repositories.
- Distinguish source control from data volume. A low-volume source with privileged placement, repeated sampling, high weights, trusted labels, or targeted examples can have disproportionate training influence.
- Explain provenance as a detection/investigation aid rather than proof of cleanliness. Source identity, signatures, hashes, collection time, contributor identity, transformations, versions, and lineage can help identify suspicious changes while a fully traceable source can still be malicious or compromised.
- Explain source authentication separately from semantic correctness. Cryptographically authentic data can contain poisoned labels/content supplied by an authorized but malicious/compromised source; authentication establishes origin/integrity under assumptions, not benign intent.
- Explain contributor/access controls as prevention layers. Restrict who can add/modify data, require review/approval for high-impact sources, separate duties, protect storage/ingestion credentials, and audit changes where the threat model justifies it.
- Explain dataset/version immutability and change review as useful controls. Reproducible snapshots, hashes, manifests, diffs, lineage, and approved release processes can make unexpected insertions/removals/label changes detectable and support rollback.
- Explain data validation as conditional risk reduction. Schema checks, deduplication, outlier detection, label-consistency analysis, source diversity checks, distribution monitoring, content scanning, and anomaly detection can catch some attacks but can miss clean-label, semantically valid, low-rate, coordinated, or adaptive poisoning.
- Do not treat outliers as synonymous with poison. Rare legitimate cases can be important, and sophisticated poisoning can resemble normal data; aggressive filtering can create its own coverage/bias failures.
- Explain robust learning/filtering only as mitigation families. Robust loss functions, influence/outlier methods, clipping, reweighting, trusted seed data, differential privacy in some settings, ensembles, or other defenses have assumptions and trade-offs and must not be presented as universal poisoning immunity.
- Explain synthetic/model-generated data risk carefully. Synthetic data is not inherently poisoned; however, compromised prompts/generators/judges/source data, malicious generation pipelines, or recursive contaminated outputs can introduce attacker-controlled examples or reinforce poisoned patterns.
- Explain feedback and online-learning risk. Systems that automatically learn from user feedback, interactions, ratings, logs, or production behavior can expose a continuously writable poisoning surface unless contribution limits, identity/abuse controls, validation, delayed updates, or trusted review constrain it.
- Explain preference/reward poisoning. Manipulated pairwise preferences, ratings, reward-model labels, critique data, or evaluator outputs can steer learned policies even when the underlying raw content is benign; the poisoned object is the supervision/feedback used for adaptation.
- Explain transfer/inheritance risk. A base model, adapter, reward model, distilled model, or derivative can inherit poisoned behavior from upstream learned artifacts or data lineage; downstream clean fine-tuning does not automatically remove a hidden backdoor or compromised representation.
- Explain model-generated labels/judges as non-authoritative. Automated labels or quality scores can scale curation but can also reproduce attacks or bias from compromised models/sources; independent validation is required according to risk.
- Explain holdout/evaluation independence. Use evaluation evidence that is sufficiently separated from the suspected poisoning path so an attacker cannot both compromise the model and the evidence used to declare it clean; one shared source/generator lineage can create correlated blind spots.
- Explain targeted testing. If triggers/classes/entities/source segments or attack hypotheses are known, test them explicitly in addition to aggregate benchmark performance because a targeted backdoor can leave average metrics nearly unchanged.
- Explain that normal aggregate performance does not prove absence of poisoning. Targeted behavior can be dormant, context-dependent, rare, or activated only by attacker-chosen inputs.
- Explain post-deployment detection. Monitor unexpected capability/behavior shifts, trigger-like patterns, source-specific errors, anomalous confidence/refusal/tool behavior, drift after updates, or complaints that correlate with data/model version changes, while recognizing that behavioral anomalies are not unique evidence of poisoning.
- Explain incident scoping across lineage. Determine which source records, dataset versions, transformations, training runs, checkpoints, adapters, reward models, downstream derivatives, indexes, and deployments consumed the compromised data before declaring recovery complete.
- Explain recovery beyond deleting bad rows. Once a model has trained on poisoned data, removing or correcting the source does not necessarily erase learned effects; recovery can require re-training/re-adaptation from a known-good checkpoint, verified unlearning where evidence supports it, replacing upstream artifacts, or restoring a clean model/data lineage.
- Treat rollback as evidence-based. A prior checkpoint is useful only if its training/data lineage predates the compromise and its dependencies are clean; rolling back model weights while reusing poisoned data or a compromised pipeline can recreate the attack.
- Explain data deletion propagation. Poisoned or compromised examples can persist in caches, derived datasets, shards, generated augmentations, preference sets, embeddings, snapshots, mirrors, or downstream training corpora and may need coordinated invalidation/removal.
- Explain confidentiality/privacy/fairness/safety impacts as possible consequences rather than the definition. Poisoning can create discriminatory behavior, unsafe outputs, privacy leakage, misinformation, or malicious tool behavior, while the attack remains categorized by its compromised learning-data path.
- Explain denial/resource effects where relevant. Poisoning can force costly retraining, degrade convergence, inflate filtering/review work, or create operational incidents; these impacts supplement rather than replace the core persistent model-integrity objective.
- Treat mitigations as defense in depth with residual risk. Source controls, provenance, filtering, robust training, trusted holdouts, anomaly detection, review, versioning, monitoring, and rollback address different stages and none proves a dataset/model poison-free.
- Require security claims to identify model/data/training versions and attack assumptions. Poisoning susceptibility and defense effectiveness can change with data scale/composition, model architecture, objective, optimizer, fine-tuning method, sampling, filtering, and attacker access.
- Keep concrete poisoned examples/datasets, attack payloads/triggers, compromised sources, model/provider vulnerabilities, current incidents, benchmark/red-team results, detection tools, thresholds, clean-room recovery procedures, and project-specific threat models with their applicable evidence/catalog/project owners.
- Use the canonical entity references as research inputs for current adversarial-ML poisoning taxonomy and Generative-AI data/model-poisoning boundaries when reader-facing rendering is activated.

## Validation

- Data poisoning requires an adversarial learning/update-data manipulation boundary and is not equated with every data-quality defect, bias, duplicate, stale record, or distribution shift.
- Prompt injection, retrieval poisoning, evaluation contamination, data leakage, and model/software artifact tampering remain distinct but potentially composable attack/problem classes.
- Poisoning does not require label flipping, a large contaminated fraction, a backdoor trigger, or broad aggregate-performance degradation.
- Provenance, signatures, filtering, anomaly detection, robust training, or normal benchmark performance is not presented as proof of absence.
- Recovery accounts for persistent learned effects and downstream lineage rather than assuming source-row deletion alone cleans an already trained model.
- Concrete attacks, triggers, datasets, incidents, model/provider vulnerability claims, detection thresholds, and project recovery plans remain outside the reusable data-poisoning concept.
