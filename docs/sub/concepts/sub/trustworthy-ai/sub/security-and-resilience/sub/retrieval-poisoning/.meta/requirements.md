# Documentation Requirements

## Requirements

- Use the reader-facing title `Retrieval Poisoning`.
- Define retrieval poisoning as an adversarial retrieval-security attack family in which an attacker intentionally inserts, removes, modifies, relabels, ranks, indexes, or otherwise manipulates external retrievable knowledge/evidence or retrieval state so later queries surface attacker-controlled or attacker-favored content and thereby influence an AI application's answer, decision, context, or action.
- Keep adversarial intent or attacker-controlled manipulation explicit. Stale documents, ordinary indexing mistakes, accidental corruption, low-quality sources, contradictory evidence, broken chunking, or poor retrieval relevance can cause serious information-integrity failures but are not poisoning unless an adversary deliberately creates or exploits the manipulation as an attack.
- Use `retrieval poisoning` as the broader AI Lab concept term while explaining that current MITRE ATLAS names its RAG-specific technique `RAG Poisoning` (`AML.T0070`). Do not imply that every retrieval system is RAG or that the MITRE technique name defines the only possible retrieval-poisoning implementation.
- Keep the attack at the external retrieval/evidence layer rather than requiring persistent model-parameter modification. The poisoned state can live in documents, records, chunks, source repositories, vector stores, embeddings/index state, knowledge graphs, search indexes, metadata, ranking/relevance inputs, filters, or other retrievable structures used later during application/inference.
- Do not require direct write access to the vector database or index. An attacker can poison an upstream wiki, shared drive, public webpage, user-contributed corpus, external feed, connector source, document store, knowledge graph, or other location that a trusted ingestion/indexing pipeline later imports.
- Distinguish retrieval poisoning from `data-poisoning/`. Data poisoning compromises persistent learning/adaptation data or supervision so the attack is learned into model/policy state; retrieval poisoning compromises external evidence or retrieval state used at application/inference time without necessarily changing model parameters.
- Distinguish retrieval poisoning from `prompt-injection/` and `prompt-injection/indirect-prompt-injection/`. Retrieval poisoning is defined by manipulation of what is retrieved; indirect prompt injection is defined by malicious instruction-like content reaching the model through a separate data/resource channel. A poisoned retrieval item can realize both attacks when it is retrieved and then interpreted as instructions, but neither concept subsumes the other.
- Explain that retrieval poisoning can operate through malicious knowledge rather than instructions. False claims, forged records, biased descriptions, manipulated entity facts, fabricated citations, or attacker-chosen evidence can steer an answer even when the poisoned content contains no command to the model.
- Distinguish retrieval poisoning from misinformation/disinformation as content/outcome categories. Poisoning describes the adversarial retrieval path; false or misleading information can be the payload or impact, but truthful-looking or instruction-bearing content can also be used to manipulate retrieval behavior.
- Distinguish retrieval poisoning from hallucination. A model can faithfully ground an answer in poisoned retrieved evidence and still produce an attacker-influenced false answer; citation or retrieval grounding therefore does not prove semantic correctness or source trustworthiness.
- Distinguish retrieval poisoning from direct model/artifact or software/supply-chain compromise. Replacing model weights, modifying checkpoint files, altering retriever code, compromising a dependency, or tampering with deployment software is a different attack path even if it changes retrieval or generated output.
- Explain persistence at the retrieval layer. Once malicious content is stored or indexed, it can influence future benign users or queries without the attacker interacting with each request, until the poisoned source and derived retrieval state are removed or cease to rank.
- Explain targeted versus broad objectives. A targeted poison can be crafted to surface for specific questions, entities, users, topics, or triggers while leaving unrelated retrieval apparently normal; broader poisoning can bias a domain, degrade retrieval quality, spread malicious instructions, or create systemic misinformation.
- Explain the retrieval condition separately from downstream influence. An attack normally needs the malicious item to be admitted/indexed and retrieved with sufficient rank or selection probability; influencing generation, decision, or tool behavior is an additional downstream condition and can fail even when retrieval succeeds.
- Do not require a large poisoned fraction. Research demonstrates that a small number of strategically crafted records can have high influence for selected queries in some RAG configurations; effectiveness depends on retriever, corpus, ranking, prompts, generator, query distribution, attacker knowledge, and defenses.
- Explain attacker knowledge and access as variables rather than prerequisites fixed by the concept. Attacks can be black-box or white-box and can exploit public ingestion, authorized contributor roles, compromised accounts, insiders, upstream content ownership, shared repositories, connector permissions, or direct index access.
- Explain content-placement and ranking manipulation together. An attacker may craft semantic content, keywords, metadata, embeddings, repetitions, links/graph structure, document placement, query-targeted text, or other features so poisoned entries are admitted and preferentially retrieved; no single ranking algorithm is required.
- Do not equate embeddings with the attack definition. An attacker may manipulate embedding/vector state directly, but simply planting malicious source text that a legitimate pipeline embeds and indexes can also create retrieval poisoning.
- Treat knowledge-graph and structured retrieval poisoning as in scope when the graph/records are external evidence used for later retrieval. Malicious nodes, edges, attributes, labels, aliases, provenance fields, or ranking metadata can influence retrieval without changing model parameters.
- Explain multi-stage ingestion risk. Parsing, OCR, document conversion, chunking, metadata extraction, embedding, deduplication, indexing, graph construction, synchronization, and federation can each preserve, amplify, hide, or transform attacker-controlled content; a clean final index format does not prove the source was benign.
- Explain source authentication separately from semantic correctness. Signatures, hashes, authenticated connectors, or trusted contributor identities can establish origin/integrity under assumptions but cannot prove that an authorized, compromised, or malicious source supplied truthful or safe content.
- Explain provenance as a detection/investigation aid rather than proof of trust. Preserve source identity, origin URL/path, contributor, ingestion time, transformations, chunk lineage, document/index version, and applicable authorization so suspicious retrieved content can be traced and invalidated.
- Explain ingestion/access controls as prevention layers. Restrict who and what sources can enter high-trust corpora, separate tenant/role scopes, require review for sensitive sources, protect connector/index credentials, and audit write/sync operations according to the threat model.
- Explain source allowlists and trust tiers carefully. Limiting ingestion to approved sources can reduce exposure but does not make those sources uncompromisable, current, unbiased, or semantically correct; high-trust sources still require monitoring and recovery paths.
- Explain versioned, reproducible retrieval state as a control. Immutable source snapshots, manifests, hashes, index build provenance, configuration versions, and reproducible re-indexing can make unexpected changes visible and support recovery to a known-good state.
- Explain retrieval-time filtering and validation as conditional mitigation. Content scanners, prompt-injection detectors, schema checks, policy filters, malware checks, anomaly detection, duplicate detection, source validation, and semantic consistency checks can catch some attacks but can miss novel, obfuscated, clean-looking, multilingual, multimodal, low-rate, or context-dependent poisons.
- Explain ranking and source-diversity controls as mitigation families rather than guarantees. Trust-aware ranking, source constraints, diversity requirements, corroboration, deduplication, confidence thresholds, reranking, and multiple independent sources can reduce single-source influence while introducing their own assumptions and failure modes.
- Explain that relevance is not trust. High vector similarity, lexical match, reranker score, graph proximity, recency, popularity, or repeated presence can make content easy to retrieve without proving that it is authorized, authentic, non-malicious, or correct.
- Explain that citations are not proof of safety or correctness. A response can accurately cite a poisoned source; citation quality depends on source provenance, support, interpretation, and the absence of adversarial manipulation, not merely on the presence of a reference.
- Treat retrieved content as untrusted with respect to control authority. Retrieved evidence may inform generation, but it must not by itself gain permission to override system/application policy, expose secrets, broaden data scope, invoke privileged tools, or authorize consequential actions.
- Explain separation of evidence from instructions where useful. Systems can parse or summarize retrieved content into constrained data structures, strip unsupported control fields, and require separately authorized logic for actions, while recognizing that structural separation alone does not eliminate semantic manipulation or model-level injection risk.
- Explain least privilege and tenant isolation for retrieval systems. Index/query/write permissions, connector credentials, namespaces, filters, document ACLs, and tool scopes should match the requesting identity and task; shared vector stores or caches must not collapse tenant or authorization boundaries.
- Explain monitoring across both ingestion and retrieval. Useful signals can include unexpected source additions/changes, unusual contributors, bulk syncs, index rebuilds, changed hashes, retrieval of newly introduced documents, abnormal rank concentration, repeated target-query matches, suspicious instruction-like content, and behavior shifts tied to source/index versions.
- Do not treat anomalous retrieval as proof of poisoning. Legitimate breaking news, rare documents, taxonomy changes, migrations, or corpus updates can look unusual; investigation must connect suspicious state to adversarial manipulation and system impact.
- Explain adversarial evaluation using realistic attack surfaces. Test attacker-controlled source insertion, modified documents/metadata, retrieval-targeted false evidence, instruction-bearing poison, conflicting sources, relevant-but-malicious chunks, direct index writes when applicable, and benign controls across representative queries and system versions.
- Keep knowledge-corruption and prompt-injection variants separately measurable during evaluation. A system can resist malicious instructions yet still accept false evidence, or reject false claims while remaining vulnerable to instruction-bearing retrieved content.
- Explain recovery beyond deleting the visible source. Poisoned material can persist in chunks, embeddings, vector indexes, search caches, graph projections, snapshots, replicas, summaries, derived corpora, connector mirrors, conversation memory, or downstream stores and may require coordinated invalidation and rebuild.
- Require compromise-aware re-indexing. Rebuilding an index from the same still-poisoned upstream source, compromised connector, stale snapshot, or malicious transformation pipeline can immediately recreate the attack.
- Explain incident scoping across retrieval lineage. Determine which sources, document versions, chunks, embeddings/index generations, graphs, caches, queries, conversations, generated outputs, decisions, tool actions, and downstream consumers were affected before declaring recovery complete.
- Treat rollback as evidence-based. A prior index or snapshot is useful only if its source lineage and pipeline predate the compromise and its access/configuration state is known good; rollback alone does not fix leaked credentials or an attacker-controlled upstream source.
- Explain post-recovery validation. Rebuild from verified sources when necessary, re-run representative and adversarial retrieval tests, verify authorization boundaries and provenance, and monitor for reintroduction before restoring ordinary trust or automation levels.
- Treat mitigations as defense in depth with residual risk. Source/access controls, provenance, content validation, ranking defenses, isolation, least privilege, monitoring, adversarial testing, invalidation, and recovery address different stages; no generic combination should be presented as universal immunity to retrieval poisoning.
- Require security claims to identify the retrieval system/version and attack assumptions. Corpus/index version, ingestion sources, retriever/embedding/reranker, chunking, query processing, generator, tool permissions, tenant model, and attacker access can materially change susceptibility and defense effectiveness.
- Keep concrete poisoned documents/records, attack payloads, target queries, current vulnerabilities/incidents, benchmark or red-team results, detection products/thresholds, index configurations, source allowlists, and project-specific threat models/recovery runbooks with their applicable evidence/catalog/project owners.
- Use the canonical entity references as research inputs for current MITRE RAG-poisoning taxonomy, peer-reviewed knowledge-corruption attack evidence, and OWASP vector/RAG security boundaries when reader-facing rendering is activated.

## Validation

- Retrieval poisoning requires an adversarial external-retrieval/evidence manipulation boundary and is not equated with every stale, incorrect, conflicting, low-quality, or badly indexed source.
- Data poisoning, retrieval poisoning, prompt injection, indirect prompt injection, hallucination, misinformation, and model/software supply-chain compromise remain distinct but potentially composable attack/problem classes.
- Retrieval poisoning does not require direct vector-database access, manipulated embeddings, instruction-like payloads, model-parameter changes, a large poisoned corpus fraction, or broad degradation across all queries.
- A relevant/high-ranking retrieved item, authenticated source, citation, provenance record, filter pass, or normal aggregate retrieval quality is not presented as proof that the retrieved evidence is benign or correct.
- Consequential permissions and side effects remain protected by deterministic authorization/validation outside retrieved content and model behavior.
- Recovery accounts for derived indexes, embeddings, chunks, caches, replicas, and upstream source/control compromise rather than assuming deletion of one visible document cleans the system.
- Concrete attacks, payloads, incidents, current product/model vulnerabilities, benchmark results, detector thresholds, and project recovery procedures remain outside the reusable retrieval-poisoning concept.
