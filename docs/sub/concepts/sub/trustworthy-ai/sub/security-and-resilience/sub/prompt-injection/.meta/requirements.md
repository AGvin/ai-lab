# Documentation Requirements

## Requirements

- Use the reader-facing title `Prompt Injection`.
- Define prompt injection as a Generative-AI/application security vulnerability and attack family in which attacker-controlled or otherwise untrusted instruction-like input causes a model/application to treat data as higher-authority instructions, altering behavior contrary to the intended instruction, authorization, or task policy.
- Keep the concept system-level rather than model-only. Prompt injection risk arises from the combination of instruction-following model behavior, how applications combine trusted instructions with untrusted content, available data/tools/permissions, output handling, and surrounding deterministic controls.
- Distinguish prompt injection from ordinary user prompting. A user asking the model to perform a legitimate task or changing preferences within their authorized scope is not a security injection merely because it changes model behavior.
- Distinguish prompt injection from benign instruction conflict. Conflicting documents, user text, or examples can accidentally alter behavior; security treatment focuses on untrusted/adversarial instruction influence or vulnerabilities where data can cross an authority boundary the application intended to enforce.
- Explain direct prompt injection as a subtype/attack path in which the primary user/attacker provides the injection through the normal query/input channel. Keep it as terminology within this parent; do not infer a `direct-prompt-injection/` child without a separately selected substantive node.
- Keep `indirect-prompt-injection/` as the selected child for attacks delivered through external/resource content that the system later reads, retrieves, processes, or observes.
- Distinguish prompt injection from jailbreaking. Jailbreaking commonly targets bypass of model safety/alignment restrictions; prompt injection more broadly targets instruction/control boundaries and can redirect application goals, manipulate tools, expose data, or alter decisions even when no content-safety rule is being bypassed.
- Distinguish prompt injection from data/model poisoning. Poisoning modifies persistent training, adaptation, retrieval/index, source, or other upstream data/artifacts to influence later behavior; prompt injection operates through instruction-like inference/application inputs, though a poisoned resource can be used to deliver an indirect injection.
- Distinguish prompt injection from retrieval poisoning. Retrieval poisoning changes or plants content in a retrieval corpus/index so later queries return attacker-controlled information; if that retrieved content contains instruction-like payloads interpreted as commands, indirect prompt injection can be one downstream exploitation mechanism.
- Distinguish prompt injection from prompt/system-prompt extraction. An injection can attempt to reveal hidden instructions, but disclosure/extraction is an objective/impact rather than the definition of the injection attack itself.
- Distinguish prompt injection from improper output handling. An injected model output may become dangerous when downstream code executes/parses it unsafely, but the output-handling vulnerability is a separate application-security boundary.
- Do not restrict prompt injection to visible natural-language text. Models/applications can interpret hidden text, markup, code/comments, encoded content, multilingual/obfuscated strings, images, audio, documents, structured fields, or multimodal inputs as instruction-bearing content depending on the system.
- Explain authority/trust rather than token position alone. A system prompt, developer message, user input, retrieved document, tool result, or media content can have intended authority relationships, but textual ordering or a model's learned instruction hierarchy is not a deterministic security boundary.
- Explain that placing `ignore previous instructions` or similar wording in an attack is merely one example. Prompt injection does not require a specific phrase, explicit override language, or human-readable payload; the security property is unintended instruction influence across an authority boundary.
- Treat successful impact separately from attack attempt. An injection attempt can fail, partially influence output, or be contained by system controls; attack classification does not require that every objective succeeds.
- Explain common objectives as non-exhaustive examples: policy/instruction override, hidden prompt or sensitive-data disclosure, unauthorized tool/action invocation, target-output manipulation, misinformation, privilege escalation through connected functions, exfiltration, resource abuse, or denial/degradation.
- Treat side-effect capability as an impact multiplier. A read-only summarizer and an agent with email, browser, shell, database, purchasing, infrastructure, or file-write tools face different consequences even if the underlying model is equally injection-susceptible.
- Explain that model compliance with injected text is not equivalent to authorization. Every consequential tool/data/action boundary must independently validate caller/user identity, permissions, parameters, business invariants, and approval requirements.
- Explain that model refusal is not proof of security. A model can resist one payload and fail under paraphrases, multilingual/encoded/multimodal variants, different context, longer conversations, model updates, tool outputs, or future adversarial techniques.
- Do not claim system prompts alone prevent injection. Higher-priority instructions can reduce attack success while remaining probabilistic/model-dependent; secrets, permissions, and side effects require deterministic application controls outside model instruction following.
- Do not claim RAG prevents prompt injection. Retrieved evidence can itself contain malicious instructions, and relevance/grounding does not grant control authority. RAG changes the attack surface rather than eliminating it.
- Do not claim fine-tuning/alignment eliminates prompt injection. Training can improve instruction hierarchy or refusal behavior but does not create a hard separation between instruction and data across all inputs/system compositions.
- Explain input filtering as conditional mitigation rather than a complete parser/security boundary. Filters can detect known strings/patterns/categories but can miss semantic, encoded, multimodal, split, contextual, or novel attacks and can block legitimate content.
- Explain output validation as a downstream containment layer. Schema validation, allowlists, escaping, semantic/business validation, and deterministic permission checks can reduce the consequences of compromised model output even when the injection itself is not detected.
- Explain least privilege. Give the model/application only the tools, credentials, data scopes, network access, and write capability necessary for the current task; lower authority reduces blast radius when instruction following is compromised.
- Explain trust-boundary separation. External/user/retrieved/tool content can be labeled and structurally separated as untrusted data, but labels/delimiters alone are advisory to the model and must be paired with system controls that prevent untrusted content from acquiring privileges.
- Explain separation of reading from acting where useful. A low-privilege extraction/summarization stage can produce structured data that a separately authorized component validates before actions, reducing the ability of document content to directly control privileged tools.
- Explain human approval as a risk-based control for consequential side effects. Approval should expose the proposed action/parameters and relevant evidence rather than asking a human to approve opaque model reasoning.
- Explain sandboxing/containment as impact reduction. Isolated browsers/code execution/filesystems/network scopes can constrain consequences while remaining subject to their own configuration and escape assumptions.
- Explain secret minimization. Do not place credentials, private keys, unrestricted tokens, or unrelated sensitive records in model-visible context when the task does not require them; a model cannot exfiltrate data it was never allowed to observe.
- Explain monitoring and incident response. Log privacy-safe evidence of prompts/resource origins, retrieval/tool decisions, denied/approved actions, anomalous access, and security-control outcomes so suspected injection can be investigated and compromised credentials/data/actions can be contained.
- Explain testing under realistic system composition. Evaluate direct and indirect paths, tools/permissions, long context, retrieval, multimodal inputs, output handlers, multiple turns, and model/runtime versions rather than testing isolated refusal prompts only.
- Treat mitigations as defense in depth with residual risk. No current generic technique should be described as a fool-proof prevention guarantee for all prompt injection attacks and LLM-integrated systems.
- Keep concrete attack payloads, exploit strings, current model/provider susceptibility claims, CVEs/incidents, red-team findings, product filters, system-prompt templates, tool policies, and project-specific mitigations with their applicable evidence/catalog/project owners.
- Render the standard direct-child navigation from the validated materialized child set when reader-facing rendering is activated.
- Use the canonical entity references as research inputs for current NIST/OWASP prompt-injection terminology and direct/indirect boundaries when reader-facing rendering is activated.

## Validation

- Prompt injection is not equated with normal prompting, every instruction conflict, jailbreaking, poisoning, prompt extraction, or improper output handling.
- Direct and indirect injection paths are distinguished; only the selected indirect subtype becomes a child node.
- Prompt injection is not restricted to visible English text or one stereotyped override phrase.
- System prompts, RAG, fine-tuning, delimiters, and filters are not presented as deterministic complete prevention mechanisms.
- Consequential permissions/actions remain protected by deterministic authorization/validation outside model behavior.
- Model refusal on tested payloads is not treated as proof of security or absence of vulnerability.
- Concrete payloads, incidents, provider/model vulnerability claims, red-team evidence, and project controls remain outside the reusable concept owner.
- Direct-child navigation contains only currently materialized selected descendants.
