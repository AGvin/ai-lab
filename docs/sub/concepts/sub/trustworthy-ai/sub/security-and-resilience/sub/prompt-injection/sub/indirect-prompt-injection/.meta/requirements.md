# Documentation Requirements

## Requirements

- Use the reader-facing title `Indirect Prompt Injection`.
- Define indirect prompt injection as a prompt-injection attack path in which adversarial or untrusted instruction-like content is embedded in an external/resource input that a target AI application later retrieves, reads, observes, or processes, allowing an attacker to influence the model/application without supplying the payload only through the victim's direct query channel.
- Keep the concept explicitly subordinate to `prompt-injection/`. Indirect prompt injection changes the delivery/control path of the injection; it does not create a separate security family unrelated to prompt injection.
- Distinguish indirect injection from direct prompt injection. In a direct attack, the attacker controls the primary user/query input to the target interaction; in an indirect attack, the attacker controls or influences external content/resources that the victim application subsequently incorporates.
- Do not require the attacker to have an authenticated account or direct model/API session. A remote attacker can plant content on a webpage, document, email, repository issue/comment, shared file, database record, retrieval corpus, feed, image, or other source expected to be consumed later by the application.
- Do not require the injected content to be intentionally malicious in every observed incident. External content can contain conflicting instruction-like text unintentionally; the security vulnerability exists when resource data can cross the application's intended control-authority boundary, while deliberate adversarial placement defines the attack case.
- Do not restrict indirect injection to web pages or RAG. Browser agents, email assistants, document processors, coding/repository agents, ticketing systems, shared drives, calendars, messages, databases, knowledge bases, OCR/media pipelines, multimodal inputs, API/tool results, and other external-resource paths can carry instruction-like content.
- Do not restrict payloads to visible text. Hidden/white-on-white text, metadata, comments, markup, encoded strings, filenames, alt text, OCR-visible image text, steganographic/adversarial multimodal signals, transcripts, or structured fields can influence a system if its preprocessing/model interprets them.
- Distinguish indirect prompt injection from retrieval poisoning. Retrieval poisoning changes/plants source/index content so a retrieval process surfaces attacker-controlled material; indirect prompt injection is the downstream instruction-execution/influence mechanism when such content is interpreted as commands. Either can exist without the other.
- Distinguish indirect injection from ordinary malicious content. False facts, spam, malware text, toxic content, or biased documents are not prompt injection unless they exert instruction-like influence across the model/application control boundary.
- Distinguish indirect injection from source unreliability. A source can be wrong or malicious as evidence without containing an injection payload; information-integrity/source-quality controls and instruction-authority controls solve different problems.
- Explain that internal storage/indexing does not automatically make content trusted for control. A document copied into an internal RAG index, ticket system, email archive, repository, or vector database can retain attacker-controlled instructions even if ingestion itself succeeded normally.
- Explain the dual-role problem: the same external artifact can be authoritative/relevant as data for the user's task while remaining untrusted as instructions. A web page can ground a factual answer without gaining authority to send email, reveal secrets, alter the task, or call privileged tools.
- Explain provenance/grounding boundaries. Knowing where a document came from and accurately grounding claims in it can improve information integrity but does not grant the document control authority or eliminate its ability to carry an injection.
- Explain trust-boundary crossing. The critical security transition occurs when content controlled by a lower-authority source is placed into a model context where the model can interpret it alongside higher-authority instructions and its output can affect privileged components.
- Explain impact amplification by agency. A read-only model can be manipulated into misleading output; an agent with browser sessions, email, shell, file, database, purchasing, messaging, infrastructure, or other tools can turn the same injection into unauthorized side effects or data exfiltration.
- Explain data exfiltration paths beyond explicit tool calls. Injected output can encode sensitive context into URLs, Markdown/image requests, generated messages, tool parameters, files, logs, or other channels that downstream systems may transmit or render.
- Treat model/tool output as untrusted. Even if an indirect injection convinces the model to propose a privileged operation, deterministic authorization and validation should still prevent the content source from gaining privileges it never possessed.
- Explain least privilege as a primary blast-radius control. Content-reading/summarization workflows should not automatically inherit write/destructive capabilities, broad credentials, unrelated private data, or unrestricted network access.
- Explain separation of content acquisition/extraction from privileged action execution where appropriate. A low-privilege component can parse/summarize external content into a constrained schema, while a separately authorized component decides whether a proposed action is permitted.
- Explain external-content isolation/labeling as helpful but non-deterministic at the model layer. Delimiters, tags, quoting, separate messages, `treat this as data` instructions, or source labels can reduce confusion but do not constitute a hard security sandbox inside a generative model.
- Explain canonicalization/preprocessing limitations. Removing scripts/HTML, extracting visible text, OCR, sanitizing markup, or normalizing encodings can eliminate some delivery mechanisms while leaving semantic instruction payloads intact; preprocessing is not a complete prompt-injection defense.
- Explain retrieval filtering limitations. Source allowlists, reputation, signatures, ownership checks, or moderation can reduce exposure but cannot guarantee that trusted/compromised sources never contain malicious or conflicting instructions.
- Explain content trust and control authority separately. A trusted corporate document may still contain instructions intended for a human or another system that should not govern the AI agent's tool policy; trust for factual use is not necessarily trust for execution/control.
- Explain multi-hop propagation. An injected document can cause the model to generate poisoned summaries, notes, emails, code comments, tickets, memory entries, or knowledge-base content that later becomes an indirect-injection source for another model/session.
- Explain persistent-memory risks. If model-generated or retrieved instructions are written into long-term agent memory/profile/state, a one-time indirect injection can influence future sessions unless write policies, provenance, review, expiry, and cleanup are controlled.
- Explain RAG-specific risk carefully. A retriever can select an injection because it is semantically relevant to the user query; ranking quality does not determine whether the retrieved text has instruction authority. RAG improves evidence access but creates an explicit untrusted-content path into model context.
- Explain repository/code-agent risk. README files, issues, pull-request comments, code comments, generated docs, tests, build logs, package metadata, or dependency content can contain instruction-like payloads; reading source material must not grant repository/cloud/secret privileges automatically.
- Explain multimodal risk. Images, PDFs, screenshots, audio/video, QR/text overlays, metadata, or visual instructions can carry indirect payloads if multimodal/OCR/transcription components turn them into model-interpretable instructions.
- Explain user-awareness limitations. The victim user may never see the exact payload because it can be hidden in a retrieved chunk, off-screen webpage, metadata, image, email thread, backend record, or preprocessed representation; confirmation interfaces should surface proposed privileged actions rather than relying on payload visibility.
- Explain human approval as a consequential-action control, not a generic cure. Approval should show the target action, destination, data being shared, parameters, and why it is requested so a reviewer can detect a content-driven escalation.
- Explain output/context minimization. Do not expose unrelated secrets/private conversation/history/tool credentials to a model while processing attacker-controlled content; reducing accessible sensitive data reduces possible exfiltration.
- Explain egress controls where risk requires them. Network destinations, messaging recipients, file writes, URL rendering/fetching, uploads, webhooks, and tool outputs can be allowlisted or policy-checked so injected model text cannot create arbitrary outbound channels.
- Explain monitoring/provenance. Preserve privacy-safe source identity, retrieval path, content version/hash where useful, model/tool decisions, denied/approved actions, and relevant transformations so an incident can be traced back to the resource that introduced the injection.
- Explain containment/recovery. Remove/quarantine malicious source content, invalidate derived chunks/indexes/summaries/memory, rotate exposed credentials, inspect unauthorized actions, restore clean state, and re-evaluate affected workflows rather than only adding a new prompt instruction.
- Treat mitigations as layered and threat-model-specific. No general delimiter, system prompt, RAG filter, model alignment technique, classifier, or source allowlist should be presented as universally preventing indirect prompt injection.
- Keep concrete malicious webpages/documents/emails, attack payloads, vulnerable products/versions, CVEs/incidents, red-team results, filters/classifiers, tool permissions, source allowlists, and project threat models with their applicable evidence/catalog/project owners.
- Use the canonical entity references as research inputs for current indirect-prompt-injection taxonomy and resource-delivery attack boundaries when reader-facing rendering is activated.

## Validation

- Indirect prompt injection is explicitly a subtype of prompt injection distinguished by external/resource delivery rather than by one impact or payload string.
- External content can be trusted/relevant as data while remaining untrusted as instructions/control authority.
- Retrieval poisoning, misinformation/source unreliability, ordinary malicious content, and indirect prompt injection remain distinct but composable concepts.
- Internal indexing, grounding, provenance, source allowlisting, delimiters, or preprocessing is not treated as granting security/control trust or guaranteed prevention.
- Consequential tools/actions remain protected by deterministic authorization, least privilege, validation, and approval outside model instruction following.
- Multimodal, hidden, persistent-memory, and multi-hop propagation paths are included without claiming every system supports each path.
- Concrete payloads/incidents/products, current vulnerability claims, filters, allowlists, and project controls remain outside the reusable indirect-prompt-injection concept.
