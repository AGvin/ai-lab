# Documentation Requirements

## Requirements

- Use the reader-facing title `AI Alignment and Control` and introduce `model alignment` / `alignment` as common narrower terms.
- Define alignment as shaping and evaluating model/system behavior so it better conforms to explicitly specified goals, policies, constraints, intended user/operator objectives, and acceptable behavioral boundaries across relevant contexts; define control as the complementary system mechanisms that constrain, authorize, validate, monitor, intervene in, or halt behavior when model-level alignment is insufficient or uncertain.
- Make clear that alignment is not a single solved or binary property. Behavior can vary across tasks, languages, user populations, tools, system prompts, model versions, distribution shift, ambiguous/conflicting instructions, and adversarial inputs; every claim requires a stated objective/context and evidence scope.
- Distinguish alignment objectives from objective truth or universal values. Stakeholders can disagree about desired behavior, safety trade-offs, refusal boundaries, priorities, and acceptable risk; the specification/governance process determines which goals/policies are authoritative for the concrete system.
- Distinguish user intent from authorization and policy. A system can understand what a user wants while correctly refusing or constraining it because the user lacks permission, the action exceeds policy, or a higher-priority requirement applies; `helpfulness` is not unconditional compliance.
- Present alignment methods as families rather than a single pipeline: supervised/instruction tuning, preference optimization/RLHF/DPO and other feedback methods, rule/constitution-guided training, adversarial/safety training, model editing or specialized adaptation, prompt/instruction design, inference-time policy constraints, validators/critics, and combinations.
- Keep the detailed training semantics with `models/training-and-adaptation/`. This owner explains why training/adaptation methods can contribute to alignment but does not duplicate SFT, RLHF, DPO, or other method definitions.
- Explain that preference/feedback data reflects annotator/evaluator populations, instructions, candidate distributions, policies, and cultural/context assumptions. A preference dataset or reward model is not a universal representation of human values and can encode disagreement, bias, or specification error.
- Explain specification gaming/reward hacking/proxy optimization as alignment risks: optimizing a measurable reward, rubric, refusal rate, judge preference, or benchmark can improve the proxy while undermining the underlying intent or producing undesirable side effects.
- Distinguish alignment from factuality, calibration, robustness, fairness, privacy, security, and interpretability. These properties can interact with alignment goals but are not automatically obtained by an aligned/helpful/refusing model.
- Distinguish alignment from access control and application security. Authentication, authorization, least privilege, sandboxing, secret protection, tool permission checks, transaction validation, and data-access policy require deterministic system controls; never rely on model `good behavior` as the only barrier to privileged actions or protected information.
- Explain instruction/policy hierarchy as a system control problem when multiple authorities exist. System/developer/application policies, user requests, tool/data constraints, and external content need explicit precedence/trust semantics; the model should not infer authority merely from persuasive or instruction-like text.
- Treat untrusted external content and tool/retrieval data as possible attempts to redirect behavior. Detailed prompt-injection/jailbreaking/security concepts remain architecture gaps or other owners; this node only establishes that alignment alone does not eliminate adversarial manipulation risk.
- Explain over-refusal and under-refusal as distinct failure modes. Stronger safety constraints can block legitimate work, while overly compliant models can facilitate misuse; evaluate task utility and constraint satisfaction together rather than maximizing one refusal/compliance rate.
- Explain corrigibility/intervention at the system level as the ability for authorized operators/humans/controls to stop, override, redirect, review, or recover behavior when required. Detailed human oversight remains with `human-ai-interaction/oversight-and-intervention/` and system reliability/security controls retain their own owners.
- Define action/tool control separately from text generation. Systems that can modify data, execute code, send messages, spend money, control devices, or call privileged tools require stronger authorization, validation, idempotency, limits, confirmation/review, and recovery controls than purely advisory output.
- Require alignment evaluation across representative normal, ambiguous, conflicting-instruction, high-risk, multilingual, long-context, tool-use, and adversarial conditions as relevant. One benign-chat preference benchmark or refusal score is not sufficient evidence for deployed alignment.
- Evaluate both desired-behavior success and regressions: task competence/helpfulness, compliance with legitimate intent, constraint/policy adherence, truthfulness/uncertainty where required, unnecessary refusals, harmful overcompliance, reward/rubric gaming, side effects, and distribution-shift behavior.
- Distinguish model-level alignment from complete-system alignment. Retrieval sources, tools, routing/fallback, prompts/configuration, permissions, human process, and deployment policy can change whether the overall system behaves according to intended goals even if the base model is unchanged.
- Treat alignment as lifecycle-sensitive. Fine-tuning, adapters, model/provider updates, prompt/policy changes, tools, retrieval corpora, routing, evaluator changes, and new attack/user patterns can invalidate prior evidence and require re-evaluation.
- Keep concrete alignment datasets, constitutions/rule sets, reward/judge models, system prompts, provider safety policies, refusal taxonomies, tool permissions, red-team findings, evaluation scores, jurisdictional/policy decisions, and deployment controls with their applicable training, governance, project, security, or evidence owners.
- Use the canonical entity references as research inputs for human-feedback and principle-guided alignment methods plus socio-technical control/evidence boundaries when reader-facing rendering is activated.

## Validation

- Alignment is not described as a solved binary property, a synonym for RLHF, or universal agreement about values/preferences.
- User intent/helpfulness is distinguished from authorization, policy precedence, and mandatory safety/security constraints.
- Model alignment is not used as the only protection for secrets, tools, permissions, transactions, or consequential side effects.
- Preference/reward/rubric optimization is not treated as proof of underlying goal satisfaction or universal human preference.
- Factuality, security, privacy, fairness, robustness, calibration, and interpretability are not assumed to follow automatically from alignment.
- Both over-refusal and unsafe overcompliance/regression are part of evaluation where relevant.
- Concrete policies, prompts, datasets, reward/judge models, tool permissions, and alignment evidence remain outside the reusable concept owner.
