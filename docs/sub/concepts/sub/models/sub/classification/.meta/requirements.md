# Documentation Requirements

## Requirements

- Use the reader-facing title `Model Classification`.
- Explain model classification as a set of potentially independent dimensions and categories rather than one ordered scale of model quality.
- Cover the selected classification concerns at a stable conceptual level: broad model kind or scope, language-model scale, and capability-frontier position.
- Make clear that one model can belong to several classification categories simultaneously and that a label on one axis does not determine labels on another.
- Keep architecture, deployment location, access/licensing, ecosystem maturity, quantization, and hardware fit conceptually separate from language-model scale and frontier status unless a dedicated selected concept explicitly relates them.
- Treat language-model scale as context-dependent rather than as deployment shorthand, and treat frontier status as time- and scope-sensitive evidence-backed classification rather than a permanent intrinsic property.
- Render the standard direct-child navigation from the validated materialized child set when reader-facing rendering is activated.
- Do not embed mutable rankings, named current frontier models, provider marketing claims, or model-selection recommendations in this classification overview.

## Validation

- No classification dimension is presented as a synonym for architecture, deployment, licensing, maturity, quantization, or practical hardware fit.
- The page does not imply that `SLM`, `LLM`, or `frontier` alone predicts task quality, safety, cost, or suitability.
- Frontier terminology is explicitly presented as evidence- and date-sensitive when applied to a concrete model.
- Direct-child navigation contains only currently materialized direct children and does not invent unselected classification leaves.
