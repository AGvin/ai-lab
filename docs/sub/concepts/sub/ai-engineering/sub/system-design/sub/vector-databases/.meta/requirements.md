# Documentation Requirements

## Requirements

- Use the reader-facing title `Vector Databases` and introduce `vector database management system (vector DBMS)` as the more explicit systems term.
- Define a vector database as a database/data-management system designed or extended to persistently manage vector representations and execute vector-aware similarity/retrieval queries while providing database-level lifecycle and operational responsibilities around stored data and indexes.
- Distinguish a vector database from `information-retrieval/vector-search/`. Vector search owns the retrieval/query method of finding items according to vector similarity; a vector database owns storage, indexing, query execution, updates, persistence, concurrency, recovery, metadata/payload management, and other DBMS responsibilities that can expose vector search as one capability.
- Distinguish a vector database from an ANN/vector-index library. An in-memory or file-backed HNSW/IVF/flat index can perform nearest-neighbor search without providing database identity, durable managed records, update/delete semantics, transactions/concurrency, backup/recovery, access controls, or an operational query service.
- Allow both native vector-specialized systems and existing general-purpose DBMSs extended with vector types/indexes/operators. A dedicated product is not required for the abstract concept.
- Do not require approximate nearest-neighbor search. Exact/vector-scan search can be a valid database capability at small scale, for validation, or under accuracy requirements; ANN is a common optimization family rather than part of the universal definition.
- Do not require one vector-index family such as HNSW, IVF, PQ, LSH, disk graphs, tree structures, or GPU indexes. Index choice depends on vector count/dimension, update rate, memory/storage, latency, recall, filters, hardware, and workload.
- Do not require one distance/similarity measure. Cosine similarity, dot/inner product, Euclidean/L2 distance, learned metrics, binary distances, or other operators can be supported depending on the embedding/model contract and index implementation.
- Distinguish vector dimensionality/type from semantic compatibility. Equal dimensions do not make vectors from different embedding models, versions, pooling schemes, normalization policies, or preprocessing pipelines comparable.
- Treat embedding/model identity and preprocessing as part of the stored-vector contract. Changing the encoder/checkpoint, tokenizer/processor, prompt/prefix convention, pooling, normalization, or representation version can require re-embedding and rebuilding/revalidating indexes.
- Require stable source/item identity independent of vector coordinates. Stored vectors should remain associated with canonical record/document/chunk/entity IDs or equivalent identifiers so updates, deletions, provenance, re-embedding, deduplication, and result attribution can be performed reliably.
- Explain metadata/payload storage as optional but common. Vector records may include structured attributes, source IDs, timestamps, tenant IDs, versions, access labels, or application payloads; the exact schema is a database/application design choice rather than part of every vector DB.
- Distinguish metadata filtering from authorization. A filter such as `tenant_id = X` can contribute to query selection, but access control requires deterministic authentication/authorization enforcement and must not rely solely on user-supplied metadata predicates or namespaces.
- Explain filtered vector search as a database query-processing problem. Pre-filter, post-filter, inline/filter-aware traversal, iterative filtering, and other execution strategies can have different recall/latency/resource behavior depending on filter selectivity, data correlation, and index structure.
- Do not assume filters and ANN compose without accuracy/performance consequences. Highly selective or correlated filters can reduce candidate availability or force additional exploration, and stable recall guarantees can become harder than in unfiltered search.
- Explain hybrid queries as a system capability rather than a universal requirement. A vector DB may combine vector similarity with structured predicates, full-text/lexical ranking, geospatial/time constraints, graph relations, or other operators; higher-level `hybrid-retrieval/` owns retrieval semantics and evaluation across signal types.
- Distinguish query planning/optimization from retrieval quality. The DBMS can choose execution order/indexes/candidate budgets efficiently while the embedding model, query formulation, chunking, reranking, and corpus coverage still determine whether the returned items are useful for the application.
- Treat vector-search recall and application relevance as different quantities. ANN recall measures recovery relative to an exact nearest-neighbor target under a metric/index, while semantic relevance or RAG answer quality depends on the learned representation, corpus, query, filtering, reranking, and downstream generation.
- Explain index-build lifecycle. Some indexes require bulk build/training, graph construction, quantizer/codebook learning, compaction, warm-up, or background maintenance; newly inserted records may be searchable immediately, after asynchronous indexing, or through a delta structure depending on the system.
- Explain update/delete semantics explicitly. Updating source content can require replacing vectors and metadata; deletions can use immediate removal, tombstones, deferred compaction, or rebuilds. Application-visible deletion guarantees must account for every index/cache/replica that can still return the record.
- Explain freshness as a cross-system invariant. A source record, embedding, metadata, and vector index can represent different versions if ingestion/indexing is asynchronous; systems should define what `current` means and how stale derived state is detected/rebuilt.
- Treat vectors/indexes as derived state when the authoritative source is elsewhere. If vectors can be regenerated from source data plus a pinned embedding/preprocessing contract, backups and disaster-recovery policy can distinguish irreplaceable source metadata from rebuildable indexes without assuming rebuild cost is trivial.
- Explain persistence/durability as implementation-dependent. Write-ahead logs, checkpoints, object storage, replicated logs, snapshots, transactional tables, or rebuildable derived indexes are different designs; the generic concept should require an explicit durability/recovery contract rather than one mechanism.
- Explain consistency/concurrency semantics as database responsibilities where updates and queries overlap. A system may provide snapshot, eventual, read-after-write, transactional, or weaker index visibility; applications should not assume newly written/deleted vectors are immediately visible/absent without the system's documented contract.
- Explain replication/sharding/partitioning as scalability/availability design families rather than universal requirements. Single-node vector DBs can satisfy small workloads; distributed systems add placement, consistency, failure, rebalance, and cross-shard query concerns.
- Explain partitioning carefully. Collections, namespaces, partitions, shards, tenants, or index segments can reduce search scope or isolate workload, but their names and semantics vary by product and do not automatically provide security isolation.
- Explain memory/storage hierarchy trade-offs. Vector values, graph/index structures, compressed codes, metadata, caches, and candidate buffers can live in RAM, accelerator memory, SSD, object storage, or combinations; latency/recall/cost depends on access path and workload.
- Explain vector compression/quantization as a database/index optimization distinct from model quantization. Product quantization, scalar quantization, binary codes, reduced-precision stored vectors, or compressed indexes trade memory/bandwidth and potentially recall; they do not change the model weights unless a separate model optimization is performed.
- Treat online writes and search workload mix as a design dimension. High ingest/update/delete rates can contend with index maintenance or degrade query performance, while read-mostly corpora can use more expensive offline index construction.
- Explain backup/restore and disaster recovery in terms of both records and derived indexes. Restoring only vector values without metadata/source IDs/version information can produce an unusable store, while restoring an incompatible old index against new embeddings can produce semantically invalid retrieval.
- Explain multi-tenancy dimensions explicitly: authorization, quotas, storage/index isolation, noisy-neighbor controls, encryption, cache separation, backup/restore scope, and telemetry can be independent from logical collections/namespaces.
- Explain availability and failure modes. Partial replica/shard/index failure can cause query errors, incomplete candidates, stale results, degraded recall, or fallback scans; services should define whether they fail closed, degrade, retry, or surface uncertainty.
- Explain observability requirements at the database/query layer: query latency and tail percentiles, candidate/exploration counts, ANN recall proxies or periodic exact baselines, filter selectivity, index build/compaction state, ingest lag, delete lag, cache behavior, memory/storage pressure, errors, and replica/shard health can be relevant.
- Require benchmark interpretation under stated workload conditions. Dataset/vector distribution, dimensionality, metric, index parameters, hardware, concurrency, filters, update rate, target recall, warm/cold state, and client/network behavior materially affect measured throughput/latency and prevent one universal product ranking.
- Explain that a vector DB cannot repair representation/data errors. Poor embeddings, wrong preprocessing, bad chunking, missing/unauthorized source content, stale data, semantic mismatch, or incorrect metadata remain upstream/application problems even when nearest-neighbor search is technically fast and accurate.
- Explain RAG as a downstream architecture. Vector DBs are common retrieval infrastructure for RAG, but RAG can use lexical, SQL, graph, web, API, memory, or other retrieval without a vector database, and a vector DB can serve non-RAG similarity/recommendation/classification workloads.
- Keep concrete products/extensions/services such as Milvus, Qdrant, Weaviate, Pinecone, pgvector, Elasticsearch/OpenSearch vector capabilities, cloud managed offerings, versions, API schemas, index names/defaults, compatibility matrices, benchmark numbers, prices, deployment topology, and purchasing/selection recommendations with their applicable catalog/evidence/decision/project owners.
- Use the canonical entity references as research inputs for vector DBMS architecture and filtered-vector-query processing when reader-facing rendering is activated.

## Validation

- A vector database is not defined as merely a vector index/library or a container that stores arrays.
- Vector search/ANN algorithms and vector database system ownership remain distinct while their interaction is explained.
- Native vector-specialized and vector-extended general-purpose DBMS designs are both valid members of the abstract category.
- ANN, HNSW/IVF, cosine similarity, metadata filters, hybrid lexical search, distributed clustering, and one persistence model are not universal requirements.
- Same vector dimension is not treated as representation compatibility, and embedding/preprocessing versions remain explicit.
- Filtering/query planning, index freshness, updates/deletes, durability/consistency, tenancy/access control, and operational failure modes remain explicit system concerns.
- Fast/high-recall nearest-neighbor search is not treated as proof of semantic relevance, grounding, or RAG answer quality.
- Concrete products, index parameters/defaults, benchmarks, prices, hardware sizing, and selection decisions remain outside the reusable vector-databases concept.
