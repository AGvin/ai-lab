# Documentation Requirements

## Requirements

- Use the reader-facing title `Continuous Batching` and introduce `iteration-level scheduling` / `iteration-level batching` as closely related foundational terminology.
- Define continuous batching as an inference-serving scheduling pattern in which the set of requests/sequences participating in batched execution can change while iterative inference is ongoing, allowing completed, blocked, cancelled, or preempted work to leave and newly eligible work to enter without waiting for one fixed whole-request batch to drain.
- Distinguish continuous batching from static/offline batching. A static batch is assembled and normally retained as one request group through the relevant execution unit; continuous batching revisits scheduling at finer execution boundaries and can change batch membership over time.
- Distinguish continuous batching from ordinary dynamic batch formation that merely waits a short window to collect requests before launching a still-fixed batch. Dynamic pre-launch batching can coexist with continuous batching but is not equivalent to it.
- Do not require a universal one-token scheduling boundary. Autoregressive text generation commonly schedules at token/iteration or prefill/decode-step granularity, while other iterative workloads can schedule denoising steps, blocks, chunks, or other execution units. The defining property is mutable active membership across ongoing iterative execution.
- Treat continuous batching as a serving/runtime scheduling concept rather than a model architecture or intrinsic model capability. The same model can be served with static, continuous, single-request, offline-batch, or other scheduling modes depending on the runtime and workload.
- Distinguish continuous batching from model-side acceleration such as FlashAttention, speculative decoding, quantization, pruning, or kernel fusion. Those techniques change execution cost or computation; continuous batching decides which concurrent work shares execution opportunities.
- Distinguish continuous batching from tensor/model/pipeline/data parallelism. Parallelism determines how one or more computations are partitioned across devices/processes; batching/scheduling determines which requests/sequences are co-scheduled. They can be combined independently.
- Distinguish serving continuous batching from training microbatching/gradient accumulation. Training microbatches divide an optimization batch for memory or pipeline reasons, whereas serving continuous batching dynamically schedules independent inference requests without a shared training update.
- Explain active batch capacity through actual workload/resource constraints rather than request count alone. Sequence length, tokens scheduled per step, multimodal encoder work, KV-cache footprint, model state, temporary buffers, speculative branches, and device memory can determine feasible concurrency.
- Explain admission control as part of the scheduler boundary. New work should enter only when the service can satisfy memory/capacity/policy constraints; accepting unlimited requests into active execution or an unbounded queue is not continuous-batching correctness.
- Treat KV-cache/state management as a major dependency for autoregressive serving. Concurrent sequences consume persistent per-request state, and admission/preemption/eviction policies must account for that memory rather than assuming compute utilization is the only constraint.
- Explain prefill and decode as potentially heterogeneous phases. Long prompt prefills can have different compute/memory characteristics from incremental decoding; runtimes may separate, chunk, prioritize, overlap, or co-schedule these phases rather than treating every request step identically.
- Explain chunked prefill as a related scheduling technique rather than part of the universal definition. Splitting a large prefill into schedulable chunks can reduce blocking or improve mix with decode work, but continuous batching can exist without one particular chunking policy.
- Explain request completion independently. Short sequences should be able to finish and release capacity without waiting for the longest sequence that happened to share an earlier batch; this is a key distinction from inflexible fixed-batch serving.
- Explain streaming compatibility. Continuous batching can support per-request streaming while computation remains batched, but scheduling and output-delivery cadence are separate concerns; batched compute does not require clients to receive outputs at identical times.
- Explain cancellation and deadlines as scheduler inputs where supported. Cancelled or expired requests should stop consuming active capacity as soon as the runtime safely permits, while exact interruption granularity remains implementation-specific.
- Explain preemption as a policy tool rather than a requirement. A scheduler can pause/evict/recompute lower-priority work to admit other requests, but preemption has memory/recomputation/latency costs and different runtimes may avoid it or implement it differently.
- Explain priority and fairness separately from throughput. FCFS, explicit priorities, shortest-job heuristics, deadline-aware scheduling, fairness quotas, tenant policies, or other schedulers can all operate with continuous batching; no one policy is part of the definition.
- Treat starvation and tail latency as risks. A policy optimized only for aggregate throughput can repeatedly defer long prefills, low-priority tenants, or memory-heavy requests; service objectives should include fairness and bounded waiting where required.
- Do not claim continuous batching always lowers latency. It often increases hardware utilization and aggregate throughput under concurrent variable-length workloads, but TTFT, queueing delay, inter-token latency, completion latency, jitter, and tail percentiles can improve or worsen depending on load and policy.
- Explain low-load behavior. When concurrency is low, there may be little batching opportunity and scheduler overhead can dominate; continuous batching is primarily valuable when the workload provides enough overlapping work to exploit shared execution efficiently.
- Explain saturation behavior. Higher admitted concurrency can raise throughput until compute, memory bandwidth, KV capacity, host scheduling, networking, or another bottleneck saturates; beyond that point queueing and latency can rise sharply even if active batches remain full.
- Distinguish configured maximum capacity from realized batch occupancy. A runtime's maximum sequences/tokens/batch-size limit is an upper bound or policy input, not evidence that every execution step uses that many requests or that larger values are better.
- Explain workload heterogeneity. Prompt length, output length, modality, model/adapter choice, sampling mode, tool interaction, speculative decoding, structured constraints, and tenant priority can create different execution costs; continuous schedulers may group only compatible work or maintain separate queues.
- Explain compatibility constraints. Requests can share a batch only when the runtime can execute the relevant model/configuration/state together; different model versions, adapters, tensor shapes, modalities, or execution modes may require partitioned scheduling or separate workers.
- Explain interaction with caching without conflating the concepts. Prefix/context caching can reduce repeated prefill work and alter scheduler cost estimates; continuous batching remains the scheduling mechanism deciding active work.
- Explain interaction with speculative decoding without conflating the concepts. Speculative methods can change the number of tokens/branches generated or verified per scheduler step, which affects token-capacity accounting while remaining a separate inference-acceleration technique.
- Explain distributed serving boundaries. A local continuous scheduler can operate inside one worker/replica, while a higher-level router/load balancer assigns requests across replicas/nodes/models. Global routing and local batch scheduling are distinct control layers.
- Explain multi-tenant isolation. Shared batching must not bypass tenant-specific authorization, model/adapter eligibility, data/cache isolation, quotas, priority policies, or observability boundaries merely because requests share accelerator execution.
- Require evaluation under realistic arrival patterns and concurrency. Offline throughput from a pre-filled queue can hide queueing, burst handling, TTFT/inter-token regressions, fairness, cancellation, and memory-pressure behavior seen in live serving.
- Measure both service and hardware outcomes where relevant: accepted requests/second or tokens/second, utilization, TTFT, inter-token latency, end-to-end latency, queueing time, tail percentiles, active/queued sequences, preemptions/recomputations, cache pressure, and rejection/load-shed behavior.
- Treat scheduler configuration as workload-specific. Token limits, sequence limits, priorities, prefill policies, queue caps, memory watermarks, streaming cadence, and preemption rules should be tuned/evaluated against explicit SLO/cost/quality requirements rather than copied from another runtime or benchmark.
- Keep concrete serving runtimes, scheduler implementations/classes, CLI flags, configuration defaults, token/sequence limits, benchmark results, deployment sizes, hardware capacities, SLO thresholds, and tuning recommendations with their applicable catalog/evidence/project owners.
- Use the canonical entity references as research inputs for iteration-level scheduling and current inference-server scheduler boundaries when reader-facing rendering is activated.

## Validation

- Continuous batching is defined by mutable active batch membership during iterative serving, not merely by large batches or a pre-launch batching window.
- No universal one-token/one-model/one-runtime scheduling algorithm is presented as required.
- Static/dynamic request batching, training microbatching, model/device parallelism, and model-side acceleration remain distinct concepts.
- Throughput/utilization improvement is not claimed to guarantee better TTFT, inter-token latency, tail latency, fairness, or cost for every workload.
- Admission, memory/KV capacity, queueing, priorities/fairness, preemption/cancellation, and realistic load evaluation remain explicit serving concerns.
- Concrete runtimes, flags, limits, benchmarks, hardware sizing, and tuning decisions remain outside the reusable continuous-batching concept.
