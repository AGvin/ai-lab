# Documentation Requirements

## Requirements

- Use the reader-facing title `GraphRAG` and introduce `Graph Retrieval-Augmented Generation` / `Graph RAG` as equivalent generic terms.
- Define GraphRAG as a Retrieval-Augmented Generation architecture/pattern family that uses graph structure or graph-derived organization during indexing, retrieval, context assembly, reasoning support, generation, or combinations so relationships and higher-order structure can influence what external evidence is supplied to a model.
- Keep GraphRAG subordinate to the canonical `rag/` concept. It remains retrieval-augmented generation: external or derived information is selected/organized at inference time to support generation; graph structure changes the knowledge organization/retrieval/integration strategy rather than replacing the RAG concept.
- Do not define generic GraphRAG solely by Microsoft's GraphRAG implementation. Entity extraction, community detection, community summaries, global/local/DRIFT search, and related Microsoft methods are influential concrete techniques, not universal requirements for every graph-based RAG system.
- Distinguish GraphRAG from a knowledge graph. `reasoning-and-decision-making/knowledge-representation/knowledge-graphs/` owns graph-organized knowledge representation; GraphRAG owns a system pattern that may retrieve from, construct, traverse, summarize, or otherwise exploit a knowledge graph or another graph structure as part of RAG.
- Do not require the graph to be a formal knowledge graph. GraphRAG can use citation graphs, dependency graphs, document/entity graphs, hierarchical/community graphs, social/organizational graphs, event graphs, code graphs, scene graphs, provenance graphs, or other relational structures when they are meaningful to retrieval/generation.
- Distinguish GraphRAG from graph databases. A graph database can store/query graph data used by GraphRAG, but it is an implementation product/category rather than the architecture itself; GraphRAG can use in-memory, relational, vector, document, custom, or other stores.
- Do not require RDF, property graphs, a specific graph query language, one graph database, one embedding model, one LLM, or one serialization/schema. These are implementation choices.
- Describe the architecture through separable stages rather than one mandatory pipeline: graph acquisition/construction, graph indexing/representation, query interpretation, graph-guided retrieval/search, evidence/context organization, generation, and optional verification can be combined differently by system.
- Explain graph acquisition as a design choice. The graph may pre-exist as authoritative structured data, be integrated from databases/APIs, be extracted from unstructured content, be generated by models, or combine these sources; provenance and confidence must preserve those distinctions.
- Treat automatically extracted/generated nodes and edges as fallible. LLM/entity/relation extraction can create duplicates, missing links, type errors, unsupported relations, or hallucinated connections; graph structure is not automatically ground truth.
- Preserve source provenance through graph transformation where factual verification matters. Entity consolidation, relationship extraction, clustering/community summarization, graph compression, and derived summaries should retain traceability back to the evidence that supports the graph claims/context.
- Distinguish structural connectivity from semantic relevance. Nodes can be adjacent or connected through many paths without being useful to the query; graph retrieval needs relation/path/type/context semantics, ranking/filtering, or other relevance controls rather than returning connected data indiscriminately.
- Distinguish graph relationships from causality. Dependency, co-occurrence, citation, organizational membership, similarity, temporal succession, and causal relations have different meanings; a path through a graph must not be narrated as a causal chain unless the edge semantics/evidence support that interpretation.
- Explain graph-based indexing as a broad family: entity/relation extraction, graph construction, hierarchical/community organization, graph summaries, path/subgraph indexes, graph embeddings, hybrid text-vector-graph indexes, or pre-existing graph structures can provide retrieval structure.
- Explain graph-guided retrieval as a broad family: entity lookup, neighborhood expansion, path/subgraph search, multi-hop traversal, community/hierarchy selection, graph algorithms, structured queries, graph embeddings, hybrid lexical/vector retrieval, and learned retrievers can all contribute depending on the graph/task.
- Explain graph-enhanced context organization/generation separately from retrieval. Retrieved nodes/edges/subgraphs can be linearized, summarized, grouped, ranked, converted to structured context, used to drive multi-step retrieval, or supplied to tools/models; graph retrieval does not dictate one prompt format.
- Make clear that conventional lexical/vector/document retrieval and GraphRAG can be hybrid. Graph structure is useful when relationships, aggregation, hierarchy, topology, dependencies, or multi-hop context add value; simple local lookups may not justify graph construction/maintenance cost.
- Explain global/corpus-level sensemaking as one important GraphRAG use case rather than the definition. Microsoft's community-summary approach demonstrates how graph organization can support broad thematic questions, while other GraphRAG systems focus on local entity, path, multi-hop, recommendation, code/dependency, biomedical, or structured reasoning tasks.
- Treat graph construction and maintenance cost explicitly. Extraction, entity resolution, schema design, indexing, graph updates, community computation, embeddings, summaries, storage, and provenance can add latency/cost/operational complexity compared with flatter retrieval pipelines.
- Explain update/freshness semantics. When source documents or structured records change, derived graph nodes/edges, communities, summaries, embeddings, and indexes can become stale; systems need version/update/invalidation strategies appropriate to the evidence requirements.
- Distinguish GraphRAG quality into stages where practical: graph/source quality, entity/relation resolution, indexing, query interpretation, retrieval/subgraph quality, context organization, and generated-answer quality. End-to-end answer scores alone can hide graph/retrieval failures.
- Evaluate graph usefulness against appropriate non-graph baselines. Improvements should not be attributed to graph structure when they can be explained by more context, different model/embedding, extra preprocessing, larger inference budgets, or better reranking.
- Do not claim GraphRAG automatically solves hallucination, grounding, attribution, or multi-hop reasoning. It can provide richer structured evidence, while final output can still misuse, omit, invent, or incorrectly combine that evidence.
- Keep generic GraphRAG distinct from `agentic-rag/`. A GraphRAG system can be agentic when an agent dynamically plans graph/retrieval/tool actions, but graph structure and agentic control are independent architectural dimensions.
- Keep concrete GraphRAG frameworks/projects (including Microsoft GraphRAG), graph stores, schemas, extraction pipelines, prompts, query algorithms, community parameters, deployment settings, benchmark results, and project-specific graph/evidence choices with their applicable catalog/evidence/project owners.
- Use the canonical entity references as research inputs for broad GraphRAG workflow taxonomy and Microsoft's influential global-query specialization when reader-facing rendering is activated.

## Validation

- Generic GraphRAG is not equated with Microsoft GraphRAG, a knowledge graph, a graph database, RDF, or one graph retrieval algorithm.
- Graph construction/extraction output is not treated as verified truth by default.
- Structural connectivity is distinguished from semantic relevance and causal meaning.
- Graph indexing, retrieval, context organization, and generation remain separable evaluation stages.
- GraphRAG is allowed to combine graph, lexical, vector, document, and structured retrieval rather than being framed as a replacement for non-graph methods.
- GraphRAG is not claimed to guarantee grounding, factuality, attribution, or reasoning correctness.
- Concrete products, graph schemas/indexes, prompts/algorithms, deployment settings, and benchmark results remain outside the reusable architecture concept.
