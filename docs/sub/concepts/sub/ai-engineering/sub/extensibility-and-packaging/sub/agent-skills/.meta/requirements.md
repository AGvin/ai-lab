# Documentation Requirements

## Requirements

- Use the reader-facing title `Agent Skills`.
- Define an Agent Skill as a reusable, inspectable package of procedural knowledge/instructions and optional supporting resources that an AI host can discover and load when relevant so the model/system can perform a repeatable class of tasks more consistently.
- Keep the concept under `ai-engineering/extensibility-and-packaging/`. Its primary identity is portable AI capability/procedural packaging plus discovery/activation/loading lifecycle, not autonomous-agent planning, runtime interoperability, tool execution, or one concrete product.
- Explain that the current open Agent Skills standard represents a skill as a directory centred on a `SKILL.md` instruction entrypoint with optional supporting resources, while exact required filenames, frontmatter fields, field constraints, directory rules, validation, experimental fields, and conformance behavior remain specification-owned and versioned.
- Keep the reusable concept distinct from the formal Agent Skills specification artifact. The concept owns durable purpose, package/lifecycle semantics, portability boundaries, relationships, trust implications, and interpretation; normative format/schema details belong to `catalog/specifications/` after the exact artifact path is selected.
- Keep abstract Agent Skills distinct from concrete skills and collections. Individually published skills, versions, repositories, publishers, collections, registries, installation sources, and maintained artifacts remain under `catalog/agent-skills/` or other applicable catalog owners.
- Keep procedural `using Agent Skills` and `creating Agent Skills` material with `learning/` after its internal taxonomy is selected; do not turn the canonical concept node into an installation/authoring tutorial merely to preserve legacy text.
- Explain the current progressive-disclosure lifecycle at a durable level: **discovery** exposes compact metadata about available skills, **activation/loading** brings full instructions into working context when a skill is selected, and **execution** follows those instructions while loading referenced resources or using host capabilities as needed.
- Treat progressive disclosure as a context-management and capability-discovery pattern, not a security guarantee. Selective loading can reduce baseline context/attack surface but a loaded skill can still contain harmful instructions or invoke risky capabilities.
- Explain discovery metadata conceptually without freezing current field limits. A skill needs enough identity/description information for a host/model/user to understand what it does and when it applies; exact names, field constraints, metadata extensions, catalog representation, and token budgets remain versioned specification/implementation details.
- Explain model-driven and user-explicit activation as valid host patterns. A host may let the model select a relevant skill, let the user invoke one explicitly, or combine both; command syntax, UI, special invocation fields, and disable-model-invocation behavior are host/collection-specific unless standardized by the applicable current specification.
- Explain installation separately from activation. A skill can be present on disk/in a repository/registry yet never be disclosed or loaded because scope, trust, policy, compatibility, user settings, or relevance prevents activation.
- Explain execution authority separately from skill instructions. A skill can tell an AI system to read files, run scripts, call tools, use MCP-connected capabilities, or perform external actions, but it does not itself grant those tools, permissions, credentials, network access, filesystem access, or side-effect authority.
- Keep host responsibility explicit. The host/runtime controls available tools, file/network isolation, credentials, approval gates, execution environment, policy, and user/tenant authorization. A portable skill must not assume capabilities that the host has not actually granted.
- Explain bundled resources generically. Skills can include or reference scripts, detailed references, templates/assets, or other supporting files so the core instructions remain focused and additional context/code is loaded only when needed; exact directory names and allowed package contents remain specification-owned.
- Distinguish Agent Skills from prompts/templates. A prompt is instruction/context content for an interaction or reusable template; an Agent Skill adds a discoverable package identity, activation lifecycle, supporting resources, and reusable capability boundary.
- Distinguish Agent Skills from persistent repository/project instructions. Repository instructions own facts/conventions that should be continuously available in a project; a skill packages a procedure/capability intended to load only when relevant. Concrete hosts may blend these mechanisms, but their conceptual roles remain different.
- Distinguish Agent Skills from tools/function calling. Tools expose executable operations; skills provide procedural knowledge about when/how to work and can orchestrate tools. A skill without tools can still be useful, while a tool does not contain the complete reusable workflow unless separately packaged as such.
- Distinguish Agent Skills from MCP. MCP is a runtime interoperability protocol for connecting AI applications to external capabilities/context; Agent Skills package procedural knowledge/resources that may instruct use of MCP-connected capabilities. Neither is a subtype of the other.
- Distinguish Agent Skills from plugins. A plugin is generally a host/ecosystem-specific installable extension bundle that can contain skills plus agents, hooks, commands, MCP configuration, integrations, UI metadata, or other components. A skill does not require plugin packaging, and a plugin is not automatically portable across hosts.
- Distinguish Agent Skills from agent workflows/orchestration. A skill can encode a workflow, interview, review discipline, or orchestration procedure, but generic planning/decomposition/handoff/multi-agent coordination semantics remain with their applicable `agents-and-autonomy/` owners.
- Distinguish Agent Skills from agents/personas. A skill supplies reusable task procedure/knowledge to a host/model/agent; it does not necessarily define an independent agent identity, persistent role, separate model instance, autonomy boundary, or delegation participant.
- Distinguish Agent Skills from model memory/context. Loading a skill places instructions/resources into the applicable working context according to the host, but the skill is not itself persistent conversational memory, retrieval memory, or a model-parameter adaptation mechanism.
- Treat portability as conditional. Conformance to the common package format improves cross-client reuse, while actual operation can still depend on host tool names, OS/runtime packages, network access, path conventions, permissions, context limits, metadata extensions, or unsupported capabilities.
- Explain compatibility declarations as scoped requirements rather than guarantees. A package may state intended products, runtimes, dependencies, network requirements, or tools, but concrete compatibility still requires testing against the actual host/version/environment.
- Explain skill scope/precedence conceptually without universalizing directory paths. Implementations can support project-, user-, organization-, built-in-, or other scopes and deterministic collision precedence; exact locations and precedence rules are host implementation facts unless standardized.
- Explain composition carefully. Multiple skills may be useful in one workflow, but overlapping ownership, contradictory instructions, activation loops, duplicate side effects, or incompatible assumptions can reduce predictability. Composition should keep responsibilities and precedence explicit.
- Explain failure behavior as part of a good reusable procedure. Skills should identify required inputs/capabilities, stop or degrade explicitly when prerequisites are missing, and avoid fabricating unavailable tool results. Exact skill-authoring guidance belongs to learning, while the concept owns the expectation that packaged procedures need observable failure boundaries.
- Treat third-party skills as supply-chain and instruction-injection inputs. A skill can contain malicious or unsafe Markdown instructions, scripts, references, generated commands, or network behavior; reviewing only its name/description is insufficient for consequential use.
- Treat scripts and executable helpers as code, not trusted documentation. Review dependencies, filesystem/network/credential access, side effects, failure modes, and source provenance according to risk before granting execution authority.
- Apply least privilege and approval boundaries to skill-driven actions. A skill should receive only the tools/data/credentials/actions required for the current task, and consequential writes, publication, payments, deployments, destructive operations, or external communications should follow host/user authorization policy rather than skill text alone.
- Treat skill updates as behavior changes. Updating instructions, scripts, references, dependencies, activation metadata, or compatibility declarations can alter model selection, commands, data handling, or side effects; consequential workflows benefit from pinned/reviewed revisions and change inspection.
- Explain provenance/source identity separately from trust. Repository, publisher, version, tag/commit, hashes, signatures, or installer metadata can make a skill traceable/reproducible but do not prove that the skill is safe, correct, current, or suitable.
- Do not make one current installer/registry/marketplace canonical. Direct directory copies, repositories, package/skill managers, host marketplaces, organization deployment, and built-in distribution can coexist; mutable ecosystem mechanisms remain concrete platform/catalog/evidence facts.
- Keep current platform support, install paths, UI indicators, invocation syntax, preview/GA status, supported metadata extensions, marketplace commands, API upload mechanisms, and host-specific behavior outside the reusable concept owner.
- Keep concrete testing results, activation benchmarks, security incidents, malicious-skill examples, recommendations, trust ratings, compatibility matrices, and collection rankings with evidence/decision/catalog owners rather than making them timeless concept facts.
- Keep legacy source deletion blocked until the abstract concept, concrete catalog items/collections, formal specification fragment, platform-support facts, using/creating tutorials, and source/trust/recommendation fragments all have verified owners.
- Use the canonical entity references as research inputs for current Agent Skills identity, formal format boundary, progressive-disclosure lifecycle, cross-client implementation, and adoption while treating versioned normative format details as specification-owned.

## Validation

- Agent Skills are presented as portable AI capability/procedural packages, not as synonyms for prompts, tools, MCP, plugins, agents, workflows, repository instructions, or memory.
- The concept does not imply that a skill grants tool access, credentials, filesystem/network permissions, or side-effect authority.
- Discovery, installation/presence, activation/loading, and execution remain distinct states.
- Progressive disclosure is not treated as a security guarantee or mandatory identical host implementation beyond the applicable current standard.
- Formal `SKILL.md` schema/field/layout constraints remain outside the reusable concept owner.
- Concrete skills/collections, platform support, installation commands/paths, marketplace facts, tutorials, trust ratings, incidents, and compatibility results remain with their applicable owners.
- Third-party instructions/scripts are treated as reviewable supply-chain input and updates are treated as behavior-changing events.
