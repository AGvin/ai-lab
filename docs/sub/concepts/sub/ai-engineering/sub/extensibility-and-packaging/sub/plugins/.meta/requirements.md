# Documentation Requirements

## Requirements

- Use the reader-facing title `AI Plugins` and introduce `plugins` as the common shorter term.
- Define an AI plugin as a host-recognized extension unit, package, bundle, or module that can be discovered, loaded/installed/enabled, and used to extend an AI application or agent runtime with reusable capabilities, configuration, behavior, integrations, or component groups.
- Keep the concept under `ai-engineering/extensibility-and-packaging/`. Its primary identity is a host extension/package lifecycle boundary, not model behavior, autonomous-agent architecture, runtime interoperability, one concrete product, or one formal plugin format.
- Keep the generic concept deliberately broader than one package representation. Current ecosystems include manifest-based package directories as well as JavaScript/TypeScript hook modules; therefore `plugin` must not be defined universally as a directory containing `plugin.json` or any other single manifest.
- Treat Agent Plugins as one current portable plugin standard, not the definition of every AI plugin. Agent Plugins 1.0.0 establishes a vendor-neutral portability floor for Agent Skills and MCP server configuration, while client-specific features and other plugin ecosystems can use additional or different formats.
- Keep the reusable plugin concept distinct from the formal Agent Plugins specification artifact. Exact `plugin.json` schema, allowed fields, portable component locations/types, extension namespaces, path rules, environment placeholders, conformance, version identifiers, and client requirements remain with `catalog/specifications/` after the exact artifact path is selected.
- Keep vendor-specific plugin format contracts separate from the generic concept. Claude Code, Cursor, GitHub Copilot, OpenAI, OpenCode, and other hosts can define their own manifests/modules, component directories, hooks, commands, marketplaces, extensions, permissions, load order, update behavior, and compatibility rules.
- Distinguish abstract plugins from concrete plugins. Individually named plugins, plugin versions, publishers, repositories, collections, marketplace listings, maintained artifacts, and concrete host implementations remain with applicable catalog owners.
- Distinguish plugins from `agent-skills/`. Agent Skills package procedural knowledge/instructions for relevant-task loading; a plugin can distribute one or more skills together with other components, but a skill does not require plugin packaging and remains its own concept/format.
- Distinguish plugins from MCP. MCP is a runtime interoperability protocol for connecting an AI application to external capabilities/context; a plugin may package or configure an MCP server/integration without becoming MCP itself.
- Distinguish plugins from tools/function calling. Tools expose executable operations; a plugin can register, configure, or distribute tools but does not make plugin packaging itself a tool-use mechanism.
- Distinguish plugins from agents/subagents/personas. A plugin can distribute agent definitions or specialist configurations, but plugin identity concerns extension packaging/lifecycle rather than the agent's role, autonomy, planning, or coordination semantics.
- Distinguish plugins from hooks. A hook is behavior triggered at a lifecycle/event boundary; some plugin systems bundle hooks, while other systems use a plugin module primarily to return hooks. The generic plugin concept owns the extension unit, not the detailed event model.
- Distinguish plugins from commands, prompts/rules, connectors, MCP/LSP configuration, UI components, templates, and other bundled component classes. Packaging those components together does not transfer their intrinsic concept ownership to the plugin node.
- Distinguish plugins from generic software packages and dependency managers. AI plugins can be distributed through package managers or repositories, but the canonical concept exists because the host interprets them as AI-runtime/application extensions with model/agent-facing components or lifecycle behavior.
- Distinguish plugins from generic browser/application extensions where the AI-specific host/component model is absent. Use the broader software/platform owner for non-AI extension systems.
- Explain discovery separately from installation. A plugin can be visible in a marketplace, repository, local directory, configuration, or registry without being installed or active.
- Explain installation/presence separately from enablement/loading. Hosts can download/register a plugin while leaving it disabled, policy-blocked, incompatible, or unloaded until a later session or explicit action.
- Explain loading/enablement separately from execution. A plugin being enabled can register skills, agents, hooks, tools, MCP servers, or configuration, but actual execution still depends on the relevant host/model/tool/event path and authorization.
- Explain update as a behavior-changing event. New plugin versions can modify instructions, executable code, dependencies, hooks, external endpoints, component definitions, permissions, or activation behavior even when the package name remains the same.
- Explain disablement/removal separately from cleanup/revocation. Uninstalling package files or unregistering a plugin may not remove copied skills, generated configuration, cached dependencies, running processes, MCP registrations, connector authorizations, credentials, or external side effects.
- Explain marketplace/registry presence as distribution metadata rather than security proof. Review, curation, publisher identity, signatures, ratings, popularity, or standard conformance can improve evidence/provenance but do not guarantee benign behavior or appropriate permissions.
- Treat plugins as supply-chain inputs. A plugin can contain or load instructions, executable modules, scripts, hooks, dependencies, MCP configuration, remote assets, or external services that affect model behavior, data flow, and side effects.
- Treat host-specific executable plugin models as code. JavaScript/TypeScript modules, hook commands, binaries, install scripts, and dependencies require normal software-security review in addition to instruction/prompt review.
- Keep host responsibility explicit. The host/runtime owns enforcement of filesystem, shell, network, tool, account, credential, tenant-data, model-context, and side-effect permissions; plugin metadata or code does not legitimately grant itself authority beyond that enforcement boundary.
- Apply least privilege to plugin components and dependencies. A plugin should receive only the tools, data, credentials, network destinations, writable paths, and external account scopes needed for its intended use.
- Preserve user/admin policy boundaries. Organization policy can restrict marketplaces, publishers, components, permissions, or installation sources even when a plugin is structurally valid and technically compatible.
- Treat portability as scoped and evidence-based. A plugin can be portable under Agent Plugins for the standardized core while still carrying client extensions or relying on host-specific permissions, tools, UI, hooks, paths, or runtime dependencies.
- Do not infer that support for Agent Plugins implies support for every component that another plugin ecosystem calls a plugin component. Current Agent Plugins v1 standardizes Agent Skills and MCP servers as the portable core; richer host component sets remain host-specific unless later standardized.
- Explain client extensions without conflating them with the portable core. A standard-conformant package can contain namespaced client-specific data/components while preserving a shared core, but those extensions do not automatically become portable across other clients.
- Explain compatibility as multidimensional: plugin/spec version, host/version, component types, client extensions, runtime/OS/dependencies, permissions, transports/integrations, marketplace policy, and optional capabilities can all affect whether a plugin works as intended.
- Treat plugin naming/identity separately from publisher/source identity. Similar names across marketplaces or hosts do not prove common origin, compatibility, or behavioral equivalence.
- Treat package provenance/version pinning as useful control evidence. Repository URLs, commit/tag/version identifiers, hashes, signatures, and reviewed diffs can make behavior changes more traceable without proving safety by themselves.
- Explain composition risks. Multiple plugins can collide in names, commands, agents, hooks, tools, environment variables, MCP registrations, instructions, configuration, or event ordering; hosts need deterministic conflict/precedence semantics appropriate to their ecosystem.
- Explain failure layers. Package validation, installation, component discovery, dependency loading, hook execution, MCP startup, tool action, and user/business outcome are distinct success/failure states and must not be collapsed into `plugin installed successfully`.
- Keep mutable platform support, current commands/install paths, marketplace availability, component matrices, preview/GA status, vendor manifest fields, extension APIs, load-order details, and compatibility bugs with concrete platform/catalog/evidence owners.
- Keep concrete Agent Plugins/client conformance results, plugin security incidents, malicious-package findings, vulnerability/advisory records, rankings, recommendations, and marketplace review outcomes with evidence/decision owners.
- Keep `using plugins`, `creating plugins`, publishing, migration, testing, marketplace operation, and troubleshooting procedures with `learning/` or concrete host owners rather than the canonical plugin concept.
- Keep the legacy `plugins/using/` and `plugins/creating/` material preserved until the internal learning taxonomy provides exact destinations; concept materialization alone does not make the legacy plugin subtree deletion-ready.
- Use the canonical entity references as research inputs for the stable plugin extension boundary, the Agent Plugins portability floor, and materially different current host plugin models while treating each formal/versioned contract as specification/platform-owned.

## Validation

- AI Plugins are not defined by one manifest, directory layout, package manager, marketplace, component set, or vendor ecosystem.
- Agent Plugins is presented as one published portable standard/interoperability floor, not as a universal synonym for all plugins.
- Plugins remain distinct from Agent Skills, MCP, tools, agents, hooks, commands, connectors, prompts/rules, and generic software packages even when they bundle/configure those components.
- Discovery, installation/presence, enablement/loading, execution, update, disablement/removal, and cleanup/revocation remain distinct lifecycle states.
- Plugin validity, marketplace presence, publisher identity, signature/provenance, or standard conformance is not treated as proof of trust, safety, permission, or correctness.
- Concrete plugins/marketplaces/platform support and formal plugin specifications remain outside the reusable concept owner.
- Learning/tutorial material remains preservation-blocked until exact learning destinations are selected.
