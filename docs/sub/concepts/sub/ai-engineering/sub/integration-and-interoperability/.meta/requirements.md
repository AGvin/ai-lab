# Documentation Requirements

## Requirements

- Use the reader-facing title `AI Integration and Interoperability`.
- Define integration as connecting AI-enabled applications/components with external systems, data, capabilities, services, or other AI components so information or actions can cross an explicit interface; define interoperability as the ability of independently implemented parties to work together through shared, sufficiently compatible contracts and semantics rather than bespoke one-off coupling.
- Keep the domain AI-system-specific. It owns reusable concepts for standardized/interoperable boundaries that connect AI applications to external capabilities or other AI systems; it does not become a catch-all for every API, adapter, ETL pipeline, message bus, network protocol, or generic software integration.
- Distinguish integration/interoperability from `architectures-and-patterns/`. Architectures/patterns own reusable arrangements such as RAG, routing, fallback, and orchestration composition; interoperability concepts own the standardized/shared connection boundary that lets independently implemented components participate in such systems.
- Distinguish integration/interoperability from `system-design/`. System design owns the activity and design knowledge for composing a complete system; an interoperability concept defines a reusable cross-component contract/boundary that a system design may choose to use.
- Distinguish integration/interoperability from `agents-and-autonomy/tool-use/`. Tool use owns how models/agents select/request external capabilities and how execution is separated from model proposals; an interoperability standard can expose tools but can also exchange data, context, prompts, UI/interactivity, identity, messages, tasks, or other capabilities.
- Distinguish integration/interoperability from `agents-and-autonomy/coordination-and-communication/`. Agent coordination owns collaboration/communication behavior and organization among agents; an interoperability protocol can provide a wire/contract layer for agent communication without owning the coordination semantics themselves.
- Keep reusable concept semantics separate from formal normative specifications. A concept page explains durable purpose, scope, roles, boundaries, relationships, evolution, and interpretation; exact protocol methods/messages, schemas, transports/bindings, conformance requirements, normative security/authentication rules, version identifiers, and extension contracts remain with the selected `catalog/specifications/` artifact.
- Keep concrete implementations separate from the abstract interoperability concept. Hosts/clients/servers/agents/gateways, SDKs, frameworks, registries, adapters, products, services, plugins/extensions, and provider-specific implementations belong to their applicable catalog owners when independently identifiable.
- Explain that interoperability requires more than syntactic connectivity when the use case depends on meaning. Two implementations can exchange correctly encoded messages while still disagreeing about capability semantics, identity, authorization, task state, resource meaning, error behavior, or lifecycle assumptions; claims should identify the compatibility layer actually established.
- Explain interoperability scope explicitly. Useful dimensions can include discovery, capability advertisement/negotiation, data/context exchange, action/tool invocation, agent messaging/tasks, identity, authorization, asynchronous/streaming behavior, errors, extensions, transport/binding compatibility, and semantic expectations as applicable to the concrete standard.
- Do not imply that one protocol must cover every integration dimension. Different standards can intentionally cover complementary boundaries; for example, current MCP focuses primarily on AI-application integration with external context/data/tools/capabilities, while current A2A focuses on interoperable agent-to-agent collaboration/communication.
- Explain composition without conflation. One AI system can use multiple interoperability standards at different boundaries; using MCP for external capabilities and another protocol for agent-to-agent exchange does not make either protocol a strict extension/subset of the other unless their governing specifications say so.
- Explain roles as protocol/concept-specific rather than universal AI identities. Terms such as host, client, server, agent, provider, consumer, gateway, or registry can have precise meanings within one standard and must not be generalized automatically to every interoperability system.
- Explain capability discovery/negotiation as a common interoperability concern without requiring one mechanism. Parties need a reliable way to know which optional/required features are supported, but the exact advertisement, discovery, negotiation, fallback, and compatibility behavior is specification/version-specific.
- Explain extensibility as a compatibility concern. Extension points can let ecosystems evolve without changing a minimal core, but optional features create partial-support matrices, downgrade/fallback decisions, namespace/governance questions, and conformance boundaries that must be stated explicitly.
- Explain versioning/compatibility separately from implementation freshness. A newer implementation is not automatically compatible with every peer; compatibility can depend on protocol version, negotiated features, transport/binding, extensions, security profile, and concrete implementation behavior.
- Treat protocol evolution as expected. Durable concept documentation should avoid freezing transient methods, lifecycle steps, transport choices, primitive lists, extension names, or deprecation status as timeless identity; mutable normative details belong to the versioned specification/evidence owners.
- Explain trust and authorization boundaries as part of interoperable system design without implying that interoperability itself grants trust. Successful protocol communication or capability discovery does not authorize data access, tool execution, transactions, privilege escalation, or cross-tenant disclosure.
- Distinguish identity/authentication from authorization. A standard can establish or carry identity/authentication information while the receiving application still owns policy decisions about which resources/capabilities/actions that identity may use under the applicable protocol requirements and system policy.
- Treat descriptions, metadata, advertised capabilities, schemas, resource contents, tool annotations, agent cards, or extension metadata as claims/input whose trust level depends on source and protocol/system guarantees. Syntactic validity or successful discovery is not proof that advertised behavior is safe or truthful.
- Explain isolation and least privilege across integration boundaries. Independently connected parties should receive only the context, resources, capabilities, credentials, network/data scopes, and side-effect authority required for the intended interaction; interoperability must not collapse security boundaries merely to make integration easier.
- Explain observability and correlation as operational interoperability concerns where applicable. Requests, responses, tasks, streams, capability decisions, errors, authorization outcomes, and cross-component traces may need stable correlation/provenance while respecting privacy and secret-handling constraints.
- Explain failure semantics. Network success, protocol success, application success, and task/business success are different layers; interoperable systems need explicit timeout, cancellation, retry/idempotency, partial-failure, asynchronous-result, and error interpretation where the standard/use case requires them.
- Keep detailed generic reliability mechanisms with `ai-engineering/reliability-and-resilience/`; this domain records the interoperability boundary those mechanisms must cross rather than redefining retries/idempotency or distributed-systems reliability generally.
- Explain security evaluation separately from interoperability conformance. Two components can interoperate correctly yet be insecure, overprivileged, privacy-violating, or unsafe; conversely, strict security policy can intentionally deny a technically interoperable request.
- Require interoperability claims to identify the relevant standard/concept, versions, implementation roles, transport/binding when material, required/optional capabilities, extensions, identity/auth assumptions, and tested interaction scope. `Supports protocol X` alone is insufficient for precise compatibility decisions.
- Keep conformance/certification test results, support matrices, implementation bugs, current protocol-version adoption, provider feature availability, extension registries, interoperability incidents, and benchmark/test evidence with their applicable specification/catalog/evidence owners rather than making them timeless concept facts.
- Keep tutorials, setup guides, server/client implementation walkthroughs, interoperability labs, migration how-tos, and procedural troubleshooting with `learning/` or concrete implementation owners rather than the canonical concept owner.
- Keep `model-context-protocol/` as the currently selected direct child. Do not infer additional protocol/concept children merely because a formal specification or external standard exists; each new concept path requires architecture selection and a distinct reusable semantic need.
- Render the standard direct-child navigation from the validated materialized child set when reader-facing rendering is activated.
- Use the canonical entity references as research inputs for complementary AI interoperability boundaries while keeping their normative specification details with the formal specification owners.

## Validation

- Integration/interoperability is not used as a catch-all for generic APIs, ETL, networking, architecture patterns, tool use, or agent coordination.
- Reusable concept semantics remain separate from normative formal protocol contracts and concrete implementations.
- Interoperability is not reduced to syntactic message exchange when semantic/capability/identity/authorization compatibility matters.
- No single protocol is presented as the universal integration layer for every AI-system boundary.
- Protocol communication, discovery, or advertised capability is not treated as authorization, trust, semantic correctness, or safety by itself.
- Mutable versions, transports/bindings, extension sets, conformance results, implementation support, and current ecosystem facts remain outside the reusable parent concept.
- `model-context-protocol/` is the only currently selected direct child; additional standards are not materialized without separate architecture selection.
- Direct-child navigation contains only currently materialized selected descendants.
