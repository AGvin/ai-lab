# Documentation Requirements

## Requirements

- Use the reader-facing title `Model Context Protocol (MCP)` and introduce `MCP` as the standard abbreviation.
- Define MCP as an open interoperability protocol for connecting AI/LLM applications to external context, data, capabilities, tools, services, and other protocol-provided interaction surfaces through a standardized application/server boundary rather than bespoke integration for every provider.
- Keep the concept under `ai-engineering/integration-and-interoperability/`. MCP's durable identity is a reusable interoperability substrate/contract boundary for AI applications, not a RAG architecture, tool-calling algorithm, agent workflow, plugin packaging format, Agent Skill, or concrete software product.
- Keep the reusable concept distinct from the formal MCP specification artifact. This concept owns purpose, architectural roles, scope, relationships, evolution, and stable interpretation; exact normative methods/messages, schemas, transports/bindings, headers, authentication/authorization requirements, capability fields, extension contracts, deprecations, conformance rules, and version identifiers remain with `catalog/specifications/protocols/model-context-protocol/`.
- State the specification/version when describing behavior that is not a durable concept invariant. MCP has evolved materially across releases, so older examples, SDK behavior, blog posts, and legacy notes must not silently become current protocol truth.
- Explain the current **host / client / server** architecture at a durable role level. A host is the AI application/environment coordinating MCP integrations and policy; MCP clients act on the host side to communicate through the protocol; MCP servers expose protocol capabilities/content to connected clients. Defer precise lifecycle/cardinality/message semantics to the current formal specification.
- Do not equate the host role with a particular desktop application, agent framework, IDE, chat product, or provider. Concrete hosts/clients/servers are implementation/catalog facts; the concept owns the abstract roles.
- Explain that one host can integrate multiple independently implemented MCP servers/capability providers while retaining application-level control over which context/capabilities reach the model or downstream system. Do not imply that all servers share one trust level or authorization scope.
- Preserve the current `2026-07-28` architectural change: MCP's core protocol is stateless and no longer uses the old `initialize` / `initialized` handshake or protocol-level `Mcp-Session-Id` session model as a required lifecycle.
- Explain the stateless-core boundary carefully. `Stateless core` means the base request/response protocol does not require the former protocol-level session state; it does **not** mean MCP applications, servers, workflows, extensions, long-running tasks, subscriptions, or external systems cannot maintain state where their current contracts permit it.
- Do not preserve the legacy `initialize -> normal operation -> shutdown` sequence as timeless MCP identity. If historical lifecycle behavior is discussed, label it with the applicable older protocol version and keep the current architecture primary.
- Explain current request self-description at a high level: protocol version, client identity, and supported capabilities can accompany requests, and current MCP can support server capability discovery before normal use. Keep exact fields/method names and mandatory/optional rules specification-owned.
- Explain capabilities as versioned protocol surfaces rather than one fixed eternal list. Current servers can expose resources, prompts, tools, and extension-provided capabilities, while the protocol's core/extension split and individual primitives can evolve or be deprecated.
- Explain **resources** conceptually as server-provided data/context that applications can make available to the AI/system under host policy. Do not treat a resource as automatically trusted, authorized for every user, or equivalent to a RAG corpus.
- Explain **tools** conceptually as server-exposed callable capabilities/actions that an MCP-enabled application can invoke through the protocol. Keep detailed tool-use decision/execution semantics with `agents-and-autonomy/tool-use/`, and do not imply that an MCP tool description grants permission to execute it.
- Explain **prompts** conceptually as server-provided reusable interaction/prompt templates or prompt-related capabilities where supported by the current protocol. Keep general prompting/system-prompt semantics with the model interaction owners.
- Explain extensions as a mechanism for evolving optional capabilities outside or alongside the minimal protocol core. Keep exact extension identifiers, lifecycle, schemas, maturity/stability, and registration rules specification/catalog-owned and versioned.
- Distinguish shipped specification behavior from roadmap direction. Agentic messaging primitives, identity improvements, transport evolution, future primitive changes, or SDK priorities mentioned in roadmaps are evidence of evolution, not current normative guarantees until adopted by the relevant specification/extension release.
- Preserve historical deprecation awareness without making deprecated primitives concept invariants. Roots, Sampling, Logging, legacy HTTP+SSE behavior, Tasks/core placement, session/init behavior, and similar features have changed across MCP versions; readers should consult the formal versioned specification for exact status.
- Distinguish MCP from model/API **function calling or tool calling**. Model-side tool calling describes how a model/application represents and selects callable actions; MCP standardizes how an application interoperates with external MCP capability providers. A system can use one without the other or compose them.
- Distinguish MCP from `agents-and-autonomy/tool-use/`. MCP can carry tool capabilities but also resources, prompts, extensions, UI/interactivity or other evolving protocol surfaces, so tool use is only one relationship, not MCP's complete identity.
- Distinguish MCP from RAG. MCP can expose resources or tools used by a retrieval pipeline, but MCP does not define retrieval/indexing/chunking/ranking/grounding architecture and is not itself RAG.
- Distinguish MCP from Agent Skills. Agent Skills are portable procedural/instructional knowledge packages and discovery/activation concepts; MCP is a runtime interoperability protocol. A host/agent can use both, and a skill can instruct use of MCP-connected capabilities, without either becoming a subtype of the other.
- Distinguish MCP from plugins/extensions as a generic software packaging/distribution concept. MCP has its own protocol extension mechanism and supports concrete integrations, but `plugin` ecosystems can use different contracts, packaging, trust, installation, and lifecycle models.
- Distinguish MCP from agent-to-agent interoperability protocols. MCP can support agentic workflows and evolving messaging patterns, but its primary interoperability boundary is AI application/host to external capability/context providers. Current A2A material describes a complementary agent-to-agent boundary; do not make MCP and A2A synonyms, strict alternatives, or parent/child concepts without specification evidence.
- Distinguish MCP from general agent coordination semantics. MCP can transport messages/tasks/capabilities used in an agent system, but delegation, negotiation, group coordination, planning, supervision, handoff, and multi-agent organization remain with `agents-and-autonomy/` concepts.
- Explain local versus remote deployment as implementation/topology choices rather than concept identity. MCP integrations can cross process/machine/network boundaries according to supported transports/configuration; exact current transports and deployment requirements remain specification/implementation facts.
- Explain interoperability without implying universal compatibility. Two products both claiming MCP support can differ by protocol version, implemented capabilities, extensions, auth profile, transports/bindings, feature maturity, server/client behavior, or application policy; compatibility claims require exact scope and evidence.
- Explain capability discovery/advertisement as compatibility metadata, not trust. A server stating that it exposes a tool/resource/extension does not prove the capability is safe, truthful, authorized, correctly implemented, or appropriate for the current user/task.
- Keep host/application policy as an explicit control boundary. The AI model must not gain direct protocol authority merely because MCP exposes a capability; the host/application decides which servers, resources, prompts, tools, credentials, and actions are available under applicable policy and user/tenant context.
- Treat MCP server content/metadata/tool descriptions as potentially untrusted input unless a stronger trust relationship is established. Instruction-like content, descriptions, resource text, annotations, returned data, or UI content can affect model/application behavior and therefore require the same trust-boundary discipline as other external content.
- Distinguish user consent, authentication, and authorization. Connecting successfully or authenticating a client/server does not automatically authorize every resource/action or every end user; exact identity and authorization requirements remain specification/system-policy concerns.
- Apply least privilege across MCP boundaries. Scope credentials, servers, resources, tools, filesystem/network access, tenant data, and side-effect authority to the task/user/application context rather than granting a connected server or model broad ambient authority.
- Avoid exposing unnecessary secrets to the model or remote capability provider. Credentials should remain in host/application/server execution layers when the model only needs the resulting capability; exact secret-management mechanisms remain security/system implementation concerns.
- Explain server trust granularity. A host can trust one server/capability for a narrow purpose without trusting unrelated tools/resources/metadata or granting access to all local/contextual data. Avoid a single global `trusted MCP server` flag as a substitute for capability/resource-level policy where finer control is required.
- Explain that semantic metadata/annotations are advisory unless the current specification/system guarantees otherwise. Tool annotations, descriptions, schemas, capability metadata, server cards, or similar metadata can aid UX/policy/routing but should not become the sole security authorization boundary when supplied by a potentially untrusted party.
- Explain protocol/system security as layered. Validate inputs/outputs and schemas where applicable, enforce deterministic authorization at the consequential operation, isolate untrusted servers/tools, limit network/filesystem/data scopes, protect credentials, log material decisions, and retain recovery/revocation paths according to the threat model.
- Keep detailed prompt-injection, retrieval-poisoning, secret-handling, sandboxing, least-privilege, and trust-boundary semantics with `trustworthy-ai/security-and-resilience/`; the MCP concept establishes where those concerns arise at its integration boundary without duplicating their full definitions.
- Explain privacy/data-boundary implications without treating MCP as a privacy mechanism. Resources, prompts, tool arguments/results, identity metadata, logs, traces, and external provider calls can move sensitive data across processors/trust boundaries; data minimization, retention, residency, and provider terms remain privacy/governance/concrete-service concerns.
- Explain observability/correlation conceptually. MCP-enabled systems may need to correlate host/client/server interactions, capability decisions, failures, tool effects, and downstream outcomes for debugging/security/evaluation, while exact tracing fields/formats remain implementation/specification facts.
- Explain failures at multiple layers. Transport/protocol success does not imply the exposed tool/resource operation succeeded or that the business/task goal was achieved; applications must interpret errors, partial outcomes, retries/cancellation/idempotency, and side effects according to the concrete capability and current protocol/system contracts.
- Keep generic reliability mechanisms with `ai-engineering/reliability-and-resilience/`; MCP requirements should state the integration boundary and version-specific protocol behavior, not redefine distributed-systems reliability.
- Explain that extensions and optional features create partial interoperability. Applications should not assume every MCP peer supports every current or future capability; feature/version discovery and graceful degradation/fallback need to follow the applicable specification and product requirements.
- Keep protocol evolution visible. A concept explanation should identify major semantic shifts when they invalidate common mental models, such as the 2026 move away from required stateful sessions, while avoiding a chronological changelog that duplicates release notes/spec history.
- Require MCP compatibility/support claims to identify the concrete host/client/server implementation, protocol version(s), relevant capabilities/extensions, transport/auth assumptions, and tested scope where those facts materially affect interoperability.
- Keep concrete MCP hosts, clients, servers, SDKs, frameworks, registries, server catalogs, extensions, integrations, products, provider support matrices, version-adoption facts, implementation bugs, security advisories, incidents, conformance/evaluation results, and deployment configurations with their applicable catalog/evidence/project owners.
- Keep formal normative MCP artifacts/versions under `catalog/specifications/protocols/model-context-protocol/`; the concept owner may link to them but must not become a parallel specification authority.
- Keep procedural `using MCP`, server/client implementation walkthroughs, setup/configuration, authentication setup, debugging, deployment labs, and `creating MCP servers` tutorials with `learning/` or concrete implementation owners. The legacy `using/` and `creating/` material remains preservation-blocked until the internal learning taxonomy is selected.
- Use the canonical entity references as research inputs for the current MCP role/scope/evolution boundary while treating the formal specification as authoritative for exact current protocol behavior.

## Validation

- MCP is presented as an AI integration/interoperability protocol concept, not as a synonym for tools, RAG, agents, plugins, Agent Skills, or one concrete SDK/product.
- The formal normative MCP specification remains a separate catalog/specification owner rather than being reproduced as concept requirements.
- Host/client/server roles are preserved at a durable architectural level without retaining the obsolete required initialize/session lifecycle as current truth.
- The `2026-07-28` stateless core is not misinterpreted as a ban on application, extension, workflow, task, or external-system state.
- Resources, prompts, tools, extensions, transports, lifecycle details, and other primitives are treated as versioned/evolving surfaces rather than an immutable eternal list.
- Roadmap priorities are not presented as already shipped normative protocol behavior.
- Protocol connectivity, discovery, metadata, or tool/resource exposure is not treated as trust or authorization by itself.
- MCP support/compatibility claims are scoped by implementation/version/capabilities/extensions and do not imply universal peer compatibility.
- Concrete implementations, support matrices, formal protocol details, tutorials, security advisories/results, and project-specific configurations remain outside the reusable MCP concept owner.
