# Documentation Requirements

## Requirements

- Use the reader-facing title `Datasets` and introduce `dataset` as the singular term.
- Define a dataset as an intentionally organized collection of data units plus the structure/context needed to interpret and use that collection for one or more defined purposes such as learning, adaptation, evaluation, analysis, retrieval, calibration, simulation validation, or system development.
- Do not define a dataset by one physical file, table, database, archive, or storage technology. One logical dataset can span multiple files/shards/modalities/tables/objects, and one storage system can contain several distinct datasets or versions.
- Distinguish an abstract dataset concept from concrete dataset identities. This node owns reusable dataset semantics and lifecycle boundaries; named datasets, releases, mirrors, artifacts, endpoints, current statistics, and mutable access/license facts belong under `catalog/datasets/` or other concrete owners.
- Treat dataset identity as version-sensitive. Material changes to composition, filtering, labels, source data, preprocessing, schema, split policy, access, or correction state can create a new version/release whose results are not automatically interchangeable with earlier versions.
- Define the unit of observation/example explicitly where relevant. Rows, documents, conversations, image-caption pairs, episodes, trajectories, audio segments, graph entities/edges, events, users/items, or other units can have different dependence, duplication, sampling, and privacy semantics.
- Distinguish source observations from labels, annotations, metadata, derived fields/features, synthetic additions, augmentations, and split assignments. These components can have different provenance, quality, licensing, privacy, and validation requirements even when shipped together.
- Explain composition as more than size. Distribution across classes/groups/languages/modalities/time/geographies/domains, duplicates/correlations, missingness, long-tail cases, label availability, and source mixtures can materially determine fit for purpose.
- Scope representativeness and coverage to an explicitly defined target population/task/environment/time period. A dataset is not intrinsically `representative`; sampling frame, inclusion/exclusion rules, collection mechanisms, nonresponse/missingness, and temporal drift determine what claims are justified.
- Distinguish balance from representativeness. Artificially equal class/group counts can be useful for some learning/evaluation objectives while differing intentionally from real-world prevalence; record which distribution the dataset is meant to approximate or stress.
- Preserve provenance and lineage: identify material source(s), collection/generation method, acquisition period, transformations, filtering/deduplication, annotation/label origin, synthetic/augmented components, versions, and known dependencies needed to trace how the dataset was produced.
- Explain dataset documentation as a transparency/evidence artifact rather than a guarantee. Datasheets, Data Cards, metadata, and README-style documentation can record purpose, composition, collection, processing, uses, risks, and maintenance, but documented claims still require evidence and can become stale.
- Distinguish intended use from permitted or reliable use. Creator intent, licensing/terms, privacy/consent, technical suitability, representativeness, and downstream evidence are separate constraints; public availability does not imply unrestricted legal/ethical reuse or fitness for every task.
- Explain train/validation/test or other split roles without assuming every dataset is pre-split or iid. Splits are experimental/evaluation roles applied to data; grouping, temporal ordering, entity-level separation, leakage prevention, and repeated selection can require domain-specific split policies.
- Distinguish the generic dataset concept from `evaluation-and-measurement/evaluation-datasets/`. Any dataset can be assigned an evaluation role, but evaluation datasets have additional evidence-independence, representativeness, contamination, metric/protocol, and validity requirements owned by that evaluation node.
- Distinguish datasets from data streams and continuously evolving corpora without excluding them. A dataset can be a versioned snapshot/window over changing data or a maintained collection with explicit update policy; reproducible claims need the effective version/time boundary.
- Explain data quality as multi-dimensional and purpose-dependent. Correctness, completeness, consistency, freshness, diversity, duplication, label quality, provenance, accessibility, bias, privacy, and schema integrity can matter differently by use case; no universal scalar quality score is implied.
- Treat deduplication as relation- and purpose-dependent. Exact duplicates, near duplicates, repeated entities/events, derived variants, and semantically equivalent examples can affect leakage/effective sample size differently; removing every repetition can also destroy legitimate frequency information.
- Explain leakage/contamination at dataset boundaries. Direct duplicates are only one case; shared source documents, derived examples, temporal look-ahead, entity overlap, benchmark exposure, generated paraphrases, or labels computed from future/protected information can invalidate independence.
- Explain labels/annotations as data with their own uncertainty and provenance. Disagreement can reflect ambiguity rather than simple annotator error; label definitions, expertise, adjudication, automation/model assistance, missing labels, and policy changes must be considered when supervision/evaluation depends on them.
- Explain maintenance and deprecation. Dataset errors, takedowns, consent/access changes, stale labels, source corrections, new collection periods, schema changes, or discovered leakage can require new versions, retraction, deletion propagation, or downstream re-evaluation.
- Treat privacy/security and sensitive-content risk as lifecycle properties. A dataset can expose personal, confidential, copyrighted, secret, biometric, location, behavioral, or otherwise restricted information through raw data, metadata, labels, derived features, or membership; de-identification/public release does not automatically remove risk.
- Treat licensing, permissions, consent, and governance as concrete constraints rather than intrinsic dataset quality. Record applicable rights/obligations for the concrete dataset/version, but keep jurisdiction-specific/legal interpretation with the appropriate governance owner.
- Distinguish real, observed, simulated, synthetic, and mixed-source datasets. `synthetic-data/` owns generation semantics; this node owns the resulting dataset identity/composition/lifecycle when synthetic items form part or all of a maintained data collection.
- Keep concrete named datasets/releases, download URLs, checksums, current row counts/file sizes, licenses/terms, access credentials, mirrors, benchmark results, project-specific splits, and dataset-specific risk/acceptance decisions with their applicable catalog/evidence/project owners.
- Use the canonical entity references as research inputs for dataset lifecycle, documentation, provenance, intended-use, and versioning boundaries when reader-facing rendering is activated.

## Validation

- Dataset is not equated with one file/table/database, a static artifact, labeled supervised data, or training data only.
- Concrete dataset identities/releases remain catalog-owned rather than duplicated in the abstract concept tree.
- Representativeness/coverage claims are scoped to a target population/task/environment and sampling process.
- Documentation/public availability is not treated as proof of quality, legality, privacy, representativeness, or suitability.
- Dataset versions, provenance, labels/metadata, split roles, leakage, maintenance, and sensitive-data constraints remain explicit.
- Generic datasets and evaluation datasets are distinguished by ownership/role without duplicating evaluation-specific semantics.
- Concrete files, versions, statistics, licenses, endpoints, split artifacts, and empirical results remain outside the reusable concept owner.
